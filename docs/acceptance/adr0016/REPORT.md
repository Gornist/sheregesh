## 2. Уровень 0 — первый кадр SRTP (pi1, одна плата)

`pipelines.py` на GStreamer 1.26.2, v4l2h264enc → SRTP (AES-128-GCM) → v4l2h264dec, 127.0.0.1: 90 кадров за 3 с,
первый кадр 0,15 с, 29 к/с, потерь 0; чужой ключ и чужой SSRC — 0 кадров; PLI: 3 запроса → 3 ключевых кадра от
**аппаратного** кодера. Найдено и исправлено: на 1.26 `caps.get_structure()` отдаёт копию — ключ не доходил до
`srtpdec` (`73ae525`). Службы tx и rx на одной плате, 1280×720 6 Мбит/с: streaming за ≈ 1,05 с, 6,4 Мбит/с, jitter
0,24 мс, ключа нет в state.json и журналах, SIGTERM → 0 (`90f411c`). `rtphdrextntp64 every-packet` на 1.26.2 есть.

Найдено на платах и исправлено ночью:
1. **Кадры без дисплея не показывались** — служба rx отдаёт dmabuf (`memory:DMABuf`, `DMA_DRM`), программные
   videoscale/videoconvert его не принимают. Теперь ISP: `v4l2convert output-io-mode=dmabuf-import` (30 к/с, CPU 11 %),
   без него — GL без окна (28 %) (`f35dd7d`).
2. **Перезапуск службы rx терял видео** через ~2 мин потока: приёмник SRTP с середины потока полагает ROC = 0, а у
   передатчика уже 1 — всё отбрасывается как подложное (0 пакетов при 6,3 Мбит/с). Повтор того же ключа не лечит:
   новое сообщение **`video-renew`** (пульт → блок) → новое поколение, новый ключ и SSRC (`64cfe1d`, контракт v8).
   То же защищает от обрыва длиннее ~32 тыс. пакетов.
3. **launcher не пускал модули видео** — службы на плате упали бы (`1806df5`).
4. **OTA confirm роли console требовал `remote-tls`** — с SRTP подтверждение провалилось бы (`4d5546c`).

## 4. TLS против SRTP (60 с, 720p30, 6 Мбит/с, одна и та же сцена)

| | TLS (ADR-0011) | SRTP (ADR-0016) |
|---|---|---|
| CPU pi2 (% ядра) | агент 7,1 + gst-launch 53,5 = **61,0** | агент 2,2 + служба tx 60,8 = **63,0** |
| CPU pi1 (% ядра) | пульт 29,0 + декодер 28,4 = **58,7** | служба rx 22,3 + пульт 19,6 + ISP-приёмник 13,6 = **55,6** |
| Задержка, своя метрика | отправка → запись в декодер p50 4,7 / p95 12,4; декодер p50 19,3 / p95 22,6 мс | захват → декодировано p50 41,9 / p95 47,9 / макс 48,7 мс |

Python ушёл из пути пакетов (агент 7,1 → 2,2 %), CPU в целом — в пределах разброса. **Задержки несравнимы**: метрики
разные (у SRTP — от захвата, включая кодер; у TLS — от выхода кодера), смещение часов у SRTP — оценка пульта по
heartbeat (точность не проверена). Утверждать, что SRTP быстрее, нельзя. Устранение блокировки TCP при потерях —
не проверено (уровень 2).

## 5. Не проверено и открытые вопросы

- **Уровень 2:** потери 0/3 %, обрывы и 3 физических отключения Ethernet — нужен человек у стенда или root на платах
  (`tc netem`; у `sheregesh-ui` нет sudo, polkit не даёт). Решение владельца (ADR-0016 §7.2).
- Задержка «от стекла до стекла» и путь GL с физическим дисплеем.
- Сравнение TLS/SRTP по одной метрике «захват → декодировано» (нужна метка захвата в пути TLS или общий источник времени).
- Устройства захвата USB (YUYV/MJPEG/CVBS) через службу tx — на стенде их сейчас нет.
- Диагностика агента: `link-status.json` блока в режиме SRTP показывает транспорт `tls1.3-mutual` (телеметрия пульту
  верна — пульт видит `srtp`).
- Счётчики `srtp.auth_fail`/`replay_fail` недоступны (srtpdec их не отдаёт); `nft_dropped` — null (только root).
- У tx нет счётчика кадров кодера (`frames`/`fps` = 0).
- Откат на TLS по таймауту первого кадра проверен только тестами (на платах — выбор TLS при недоступной службе и по настройке).
- Длительный прогон 3 ч — следующий спринт (уровень 3).
