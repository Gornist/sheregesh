# 2026-11-02: аналоговый вход через USB-конвертер CVBS (MacroSilicon 534d:0021)

Итог: видео через конвертер проходит до пульта: 720×480 при 25 к/с, SRTP без потерь. По дороге найден и
исправлен дефект пульта (`b722dd5`): ISP pi1 не импортирует кадры 720×480 (dmabuf), и пульт бесконечно
перезапускал декодер. Сигнал на тюльпан во время проверки, по-видимому, не подавался: кадр чёрный. Изображение
с настоящей камеры и состояние «нет сигнала» не проверены.

**Дата:** 2026-11-02, 13:34–13:55 UTC · **Ветка:** `v2` · **Аренда:** `analog-usb` (pi1, pi2) · **Полномочия:**
владелец в чате — подключил конвертер к pi2. **Эталон:** pi1 `10000000568152de` (пульт, DEV `b722dd5`),
pi2 `100000009d497e91` (блок, DEV `gf1db02e`). Сырые данные: devbox `~/archive/acceptance/analog-usb-1102/`.

## 1. Устройство

`lsusb`: `534d:0021 MacroSilicon MS210x Video Grabber [EasierCAP]`, USB 2.0 через хаб VIA. Драйвер `uvcvideo`,
узел `/dev/video0`, «AV TO USB2.0». `python3 -m sheregesh.videoinput` относит его к входу CVBS: ID уже есть в
`CVBS_USB_IDS`. Вход один, «Camera 1»; статус сигнала UVC не сообщает. Режимы:

| Формат | Размеры | Частота |
|---|---|---|
| YUYV | 320×240, 480×320 | 5/10/20/25 |
| MJPEG | 320×240 … 720×480 | 5/10/20/25 |

Режим `auto` выбрал MJPEG 720×480@25. На блоке он декодируется программно (`jpegdec`), а не `v4l2jpegdec`,
который запрещён на pi2.

## 2. Переключение источника

В `~/.config/sheregesh/video-input.json` на pi2 был записан HDMI-захват `345f:2130:20210623`
(1280×720@60). После его отключения блок верно перешёл в «нет устройства» и не создавал новых поколений.
Настройка заменена на `{"source": "v4l2", "device": "534d:0021:20200909", "mode": "auto"}`, прежняя сохранена
в `video-input.json.before-analog`. После SIGHUP агента: `no-device -> idle`, «source back», поколение 4,
служба tx `streaming`.

## 3. Дефект пульта: ISP не импортирует кадр 720×480

Пакеты приходили (25 к/с, `seq_gaps` 0), но пульт показывал «Соединение…»: декодер выходил с
`Internal data stream error … reason error (-5)`, 17 перезапусков за минуту. Повтор вручную на pi1 с
`GST_DEBUG=v4l2*:3`: `v4l2convert output-io-mode=dmabuf-import` — `cannot import buffers from upstream` на первом
кадре (caps `DMA_DRM`, `YU12`, 720×480). При 1280×720 этот путь работал. Проверка обходных путей:

| Конвейер (100 кадров) | Итог |
|---|---|
| `v4l2convert output-io-mode=dmabuf-import` | выход с кодом 1 за 94 мс |
| `v4l2convert output-io-mode=auto` | 0, 4072 мс (25 к/с) |

Исправление `b722dd5`: если приёмник кадров службы завершился, не выдав ни одного кадра, следующий запуск идёт
через `output-io-mode=auto` (с копированием). Новый видеосеанс снова пробует импорт. Тест
`test_service_falls_back_to_copy_when_isp_cannot_import`; видеотесты GUI — 117 passed.

## 5. Не проверено и замечания

- **Изображение.** Кадр, снятый на пульте, полностью чёрный. Конвертер без сигнала отдаёт чёрное поле и не
  сообщает статус входа (см. ограничение в `videoingest.py`). Нужен источник CVBS на тюльпане.
- **«Нет сигнала»** для этого конвертера неотличимо от чёрного кадра: состояние определяется только по потоку
  кадров.
- **Путь GL с дисплеем** (`unixfdsrc → glupload`) для кадра 720×480 не проверен: на стенде нет дисплея.
- **Состояние источника на блоке** было `starting`, хотя служба tx в `streaming`: в сетевом профиле видеоприём
  агента только следит за входом и стоит в `idle`. Исправлено в `f49ce19` (раздел 6).
- **Пропорции 4:3.** Кадр 720×480 приходил с соотношением пикселей 1:1, то есть на экране 3:2 вместо 4:3
  (PAL 720×576 — 5:4). Исправлено в `49ab93b` (раздел 7); вид на дисплее не проверен — дисплея и сигнала нет.
- Копирование кадра стоит процессору пульта больше, чем импорт: для 1280×720 по-прежнему используется импорт.

## 6. Состояние входа на блоке (DEV `f49ce19` на pi2)

Агент блока в сетевом профиле берёт состояние потока у службы tx, пока вход на месте и служба передаёт
(`f49ce19`, тест `test_network_source_state_follows_tx_service`). Тесты unit/system по видео и агенту — 1325
passed. На стенде после раскатки pi2 (с `gf1db02e`): у пульта `videoSource` — `cvbs streaming`, 720×480,
25 к/с; строка состояния — «CVBS · 25 к/с». Четыре замера за минуту — без новых перезапусков приёмника,
`NRestarts=0` у служб пульта.

## 7. Пропорции 4:3 (DEV `49ab93b` на pi2)

Блок масштабирует кадр аналогового входа (тип CVBS) до квадратных пикселей 4:3 после декодирования и до кодера:
`videoscale` до ширины высота×4/3, кратной 16 (720×480 → 640×480, 720×576 → 768×576). Тесты
`test_analog_input_is_scaled_to_square_pixels_4_3`, `test_build_scales_analog_after_decode_before_encoder`;
unit/system по видео — 1327 passed.

| Показатель | До | После |
|---|---|---|
| Кадр у пульта (`unixfdsrc` caps) | 720×480 | 640×480 |
| `v4l2convert output-io-mode=dmabuf-import`, 100 кадров | выход с кодом 1 | rc 0, 4073 мс (25 к/с) |
| Декодировано / принято на пульте | 25 / 25 к/с | 25 / 25 к/с |
| Захват → декодирование, p50 / p95 | 51 / 88 мс | 50 / 86 мс |
| CPU службы tx pi2 | 17 % | 18 % |

Ширина 640 кратна 32, поэтому ISP пульта снова принимает кадр без копирования. Пульт, однажды перешедший на
копирование, остаётся на нём до нового видеосеанса службы: это дороже по процессору, но работает.
