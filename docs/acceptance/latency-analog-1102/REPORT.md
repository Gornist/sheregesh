# 2026-11-02: из чего складывается задержка видео (аналоговый USB-конвертер → пульт)

Итог: «захват → декодирование» 47–51 мс в медиане и 81–87 мс в 95-м процентиле — верная цифра, независимый замер
её подтвердил. Около 32 мс из них — передача кадра конвертером по USB. Программная цепочка (MJPEG,
масштаб, кодер, SRTP, джиттер-буфер, декодер) занимает 15–18 мс и почти не сокращается. Джиттер-буфер (20 мс)
задержки не добавляет. YUYV вместо MJPEG выигрыша не даёт. По дороге найден и исправлен дефект смены источника по
SIGHUP (`0169dc3`).

**Дата:** 2026-11-02, 14:10–14:45 UTC · **Ветка:** `v2` · **Аренда:** `latency-stages` (pi1, pi2) ·
**Полномочия:** владелец в чате — «давай» на замер по стадиям. **Стенд:** pi1 `10000000568152de` (пульт, DEV `b722dd5`),
pi2 `100000009d497e91` (блок, DEV `49ab93b`, затем `0169dc3`), конвертер MS210x `534d:0021`, сигнала на входе нет
(чёрное поле). **Средство:** `tools/probe/video_stage_latency.py` (новое). Замеры на платах — с жёстким тайм-аутом;
трассировщик GStreamer latency не применялся (вешает v4l2h264enc на pi2).

## 1. Проверка самой цифры

Метрика службы `capture_to_decoded`: PTS кадра в источнике tx (расширение RTP NTP-64) → выход декодера rx; смещение
часов пульт оценивает по heartbeat. Независимо: смещение pi2−pi1 прямым обменом UDP — **+2,96 мс** (100 проб, лучший
RTT 0,48 мс). С ним задержка кадров из сокета `frames-main.sock` (метка NTP доходит с кадром):
**p50 50,8 · p95 86,9 · min 47,1 · max 87,7 мс** (375 кадров). Служба в то же время показывала p50 37,6 мс:
оценка смещения по heartbeat плавает на ~10 мс (RTT связи 30 мс в среднем при 0,5 мс у UDP).

## 2. Стадии

| Участок | Где | p50 | p95 | Как измерено |
|---|---|---|---|---|
| Начало кадра на USB → кадр в приложении | pi2 | **32,5** | 68,5 | `v4l2src` MJPEG 720×480, время пробника − PTS драйвера |
| Распаковка MJPEG (`jpegdec`) | pi2 | 2,5 | 3,8 | стендовый конвейер, videotestsrc→jpegenc |
| Масштаб 720×480 → 640×480 | pi2 | 2,4 | 3,2 | то же |
| Кодер `v4l2h264enc` | pi2 | 4,4 | 5,8 | то же |
| Кодер → SRTP → джиттер-буфер → декодер | pi1 | 12,4–13,0 | 15,4–16,3 | пара tx/rx службы на одной плате, буфер 0/5/10/20 мс |
| Декодер `v4l2h264dec` отдельно | pi1 | 4,4 | 5,5 | стендовый конвейер |

Сумма p50: 32,5 + 4,9 + ~13 ≈ 50 мс — совпадает с замером из раздела 1. Хвост p95 (+36 мс) — интервалы кадров
конвертера: 32 мс обычно и 68 мс местами (без сигнала он идёт с частотой ~30 Гц и отдаёт 25 к/с с пропусками).

**Варианты конвертера** (тот же замер «USB → приложение»): MJPEG 720×480 — 32,5 / 68,5 мс; YUYV 480×320 — 36,3 /
64,6 мс; MJPEG 320×240 — 32,5 / 68,5 мс. Режим и размер не влияют: конвертер растягивает передачу кадра на весь
интервал.

**Не измерено:** оцифровка и сжатие внутри конвертера до первого пакета USB (обычно ещё 1 поле или кадр, 20–40 мс),
вывод на дисплей пульта (нет дисплея) и поведение с настоящим сигналом PAL/NTSC.

## 3. Что из этого следует

- Программная часть — 15–18 мс; джиттер-буфер, кодер и декодер Pi 4 уже около предела. Настройками ПО всю цифру не
  уменьшить.
- Больше всего занимает USB-конвертер: ~32 мс передачи плюс неизмеренная оцифровка. Меньшую задержку дадут только
  другое железо: аналоговый декодер на CSI-2 (например, ADV7280-M, кадр сразу в ISP без USB) или аналоговый
  приёмник прямо на экран, без оцифровки.

## 4. Дефект: смена источника по SIGHUP не доходила до службы tx

Чтобы освободить конвертер для замера, источник блока переключался на синтетический через `video-input.json` и
SIGHUP. Служба tx 30 с и дольше держала прежнее устройство: SIGHUP менял источник только у видеоприёма агента, а
новое поколение потока запускал лишь `video-select` с пульта. Исправлено в `0169dc3`: SIGHUP тоже запускает новое
поколение. Тест `test_sighup_reload_starts_new_generation`, тесты блока — 307 passed. На стенде после раскатки
устройство освобождается за 2 с, в журнале «video-key gen 2 (source changed)», возврат к CVBS — тоже 2 с, затем
поток снова идёт: 25 к/с, `capture_to_decoded` p50 45 мс.
