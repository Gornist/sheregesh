## Процедура (одна плата за раз)

Исходная microSD платы не перезаписывается: образ пишется на **отдельную** карту (не меньше 8 ГБ), исходная карта откладывается с подписью и при возврате вставляется обратно.

1. **Записать отдельную карту** на Mac скриптом `tools/image/flash_sd.py`. Рядом с образом должны лежать `SHA256SUMS` и `build-report.json` из того же артефакта.
   - `python3 tools/image/flash_sd.py build/image/ci-725e5f5-dev/sheregesh-lab-dev-pi4.img.zst` — сверяет SHA-256 и показывает внешние карты. Ничего не пишет.
   - `python3 tools/image/flash_sd.py … --disk diskN` — пишет на выбранную карту. Перед этим требует ещё раз ввести идентификатор диска, а sudo спросит пароль. После записи скрипт читает карту обратно, сверяет SHA-256 с `image_sha256` и извлекает её.
   - Скрипт не пишет на внутренние диски, на диски меньше образа или больше 256 ГБ. На карту, где уже есть система (`bootfs`/`rootfs`/…), он пишет только с флагом `--overwrite-existing`.
   - Запасной путь — Raspberry Pi Imager → Use Custom → тот же файл, на **новую** карту.
2. **Штатно выключить плату** с исходной системой: `ssh pilot@pi1.local sudo poweroff`, дождаться, пока погаснет зелёный светодиод, затем отсоединить питание. Это обычное выключение, не испытание отключением питания.
3. **Поменять карты:** исходную карту — в подписанный конверт «pi1 — исходная», новую — в плату. Кабель Ethernet тот же.
4. **Включить** плату и подождать 2–3 минуты: генерация хост-ключей SSH, инициализация раздела данных. Новый hostname — `sheregesh-dev`; mDNS в образе нет, а `systemd-networkd` получает адрес по DUID, поэтому адрес может отличаться от прежнего.
5. **Найти плату по MAC:** `python3 tools/probe/collect_boot.py find --mac d8:3a:dd:69:0e:90` (пинг подсети 192.168.1.0/24 и таблица ARP Mac) или по списку клиентов DHCP роутера.
6. **Собрать данные первой загрузки** (только чтение): `python3 tools/probe/collect_boot.py collect --host <адрес> --board pi1 --tag first-boot --out docs/acceptance/s2/pi4/<дата>/pi1`. Хост-ключ платы новый: `ssh-keygen -R <адрес>`, если адрес совпал с прежним.
7. **Обычная перезагрузка:** `ssh sheregesh-ui@<адрес> systemctl reboot` (polkit разрешает это dev-пользователю). Через 2 минуты повторить шаг 6 с `--tag after-reboot`. Сравнить: службы снова активны, слот тот же, `throttled=0x0`.
8. **Вернуть исходную систему** (по завершении или при сбое): `systemctl poweroff`, вынуть карту образа, вставить исходную.
9. После подтверждения pi1 — те же шаги для pi2 (MAC `d8:3a:dd:69:0f:6e`).

Что собирается: ОС, ядро, cmdline, активные слоты boot/system, разделы и монтирование (корень `ro`), `autoboot.txt`, состояние служб и число их перезапусков, неуспешные юниты, журналы `sheregesh-*` и ошибки загрузки, открытые порты (эмулятор — только 127.0.0.1), температура, `vcgencmd get_throttled`, `systemd-analyze`.

Ограничения: канал SHRG-LAB не выходит за loopback; плата находится в обычной локальной сети, открыт только SSH по ключу. Дисплея нет, поэтому поведение `sheregesh-console` (cage без подключённого вывода) фиксируется как есть.

Найдено и исправлено:
1. `console-setup` писал в ro `/etc` — кэш раскладки собирается при сборке (`baf0c10`, подтверждено на pi2).
2. `rpi-eeprom-update` пытался подготовить обновление EEPROM (на pi1 загрузчик 2023-01-11, доступен 2026-09-23) — служба замаскирована, обновление EEPROM выносится в отдельную явную процедуру (`baf0c10`, подтверждено на pi2). `autoboot.txt` с EEPROM 2023-01-11 работает.
3. LLMNR/mDNS на `0.0.0.0:5355` — выключены (`baf0c10`, подтверждено на pi2).
4. Сверка записи карты на macOS — запись и чтение обратно тем же дескриптором, сразу eject (подтверждено записью карты для pi2).
5. Видео эмулятора в службе: uid DynamicUser без NSS → предупреждение GLib → проба отбраковывала рабочие кодеки. Исправлено в `c36e136` (libnss-systemd, HOME, классификация вывода пробы) — **на плате ещё не подтверждено**.
6. В образе нет `ss` — сборщик читает сокеты из `/proc/net`; поиск по MAC — только отвечающий адрес.
