## 1. Аудит существующего OTA

| Компонент | Где | Что делает | Состояние |
|---|---|---|---|
| Разметка image-rota | образ: `bootconfig │ boot_a │ boot_b │ system_a │ system_b │ persistent` (32 МиБ / 256 / 256 / 2560 / 2560 / 1024) | A/B, `/dev/disk/by-slot/{active,other}`, генераторы `slot-perst-generator` (per-slot `/var`), `slot-shared-generator` (`/etc/ssh`), `machine-id` из `/persistent/common` | на обеих платах: активный A (p2/p4), `autoboot.txt` `[all] boot_partition=2`, `[tryboot] boot_partition=3` |
| Модель состояний | `software/sheregesh/update/model.py` | IDLE → VERIFIED → INSTALLING → INSTALLED → TRYBOOT → HEALTH_PENDING → COMMITTED / ROLLED_BACK, FAILED; ≤ 2 попыток пробной загрузки; основной слот меняется только в COMMITTED | без изменений логики; добавлено поле `expect` (отпечатки до переключения) |
| Слоты | `software/sheregesh/update/slots.py` | активный слот по 4 признакам (by-slot, PARTNAME, mountinfo, device-tree), запись только в other (O_EXCL, «не смонтирован»), xz → SHA-256 → fsync → повторное чтение; `autoboot.txt` в формате `rpi-slot-tryboot`; `/var` целевого слота | **исправлено**: образец `/var`, повторный перенос конфигурации |
| Агент | `software/sheregesh/update/ota.py`, сокет `sheregesh-ota.socket` (0660 root:sheregesh-ui), `sheregesh-ota-boot` | install / enable / disable / tryboot / confirm / abort; подпись манифеста `ssh-keygen -Y` (пространство `sheregesh-ota`) ДО чтения образов; tryboot/confirm только при подписанном разрешении для серийного номера платы | на платах: IDLE, переключение **не разрешено**; **исправлено**: критерии подтверждения |
| Инструмент владельца | `tools/deploy/shdeploy.py ota-*` | сборка потока, установка, разрешение, tryboot/confirm/abort по одной плате | **исправлено**: воспроизводимость, юниты и проверка образа в манифесте |
| DEV deploy | `software/sheregesh/deploy/*` | выпуски приложения в `/var/lib/sheregesh-deploy` (per-slot) | **исправлено**: время коммита у файлов выпуска |

Найденные дефекты (все исправлены, кроме отмеченного):

1. **`/var` нового слота почти пустой** (испытание на файловом образе): image-rota кладёт содержимое `/var` только на раздел persistent образа (`slots/system_X/var`, 31 МБ: `lib/dpkg`, `lib/systemd`, `lib/dbus`, `lib/polkit-1` …), на системном разделе `/var` — 20 КБ (`cache`, `log`, `spool`, `tmp`). Поток обновления несёт boot и system — агент создавал новому слоту почти пустой `/var`. Первую установку на платах выполнит агент **старого** образа `57e8fe4`, формат потока менять нельзя ⇒ исправление в новом образе: образец `/usr/share/sheregesh/var-seed.tar.gz` (снимается при сборке, воспроизводимо) и служба `sheregesh-var-seed` (первая загрузка слота с пустым `/var`: дополнить недостающее, существующее не перезаписывать); новый агент делает то же при установке (`a719b19`).
2. **Устаревшая конфигурация в новом слоте:** `/var/lib/sheregesh` переносился только при установке; изменения между установкой и tryboot терялись ⇒ перенос повторяется перед tryboot с рабочего слота; пробный слот назад не копирует (`8fd50b4`).
3. **Подтверждение только по `sheregesh-health`:** недостаточно ⇒ `confirm.py` — полный набор критериев по ролям (раздел 7) (`8fd50b4`).
4. **Пакет OTA не воспроизводим:** `created` из текущего времени, `xz -T0` (блоки зависят от числа ядер) ⇒ время из `SOURCE_DATE_EPOCH`, `--threads=4 --block-size=16MiB`; две независимые сборки — одинаковый SHA-256 (`029fd70`).
5. **`app-stop`** (`02a9b64`) и **время файлов выпуска** — исправления в `/usr`, входят в пакет (проверено в содержимом нового слота). Статус `app-stop` на плате — **ОТКРЫТ** до проверки на pi2 с обновлённым компонентом.

Риск, не исправляемый в рамках OTA: `/etc/ssh` (включая `sshd_config`) — общий каталог persistent; изменения конфигурации SSH в новом образе не применятся (ключи хоста при этом сохраняются — это и нужно).

## 2. Рекомендация по ADR-0009 — вариант **C** (для утверждения владельцем; статус ADR не менялся)

| | A. Только RAUC | B. Свой агент и в выпуске | **C. RAUC + слой слотов агента** |
|---|---|---|---|
| Решения об установке/подтверждении | RAUC | агент | **RAUC** |
| Подпись | X.509/CMS (ADR-0005), CRL | ssh-keygen → своя X.509/CRL | X.509/CMS RAUC |
| Слоты, `autoboot.txt`, «не смонтирован», `O_EXCL` | писать бэкенд с нуля | есть | **`slots.py` как бэкенд `custom` RAUC** |
| `/var`, перенос конфигурации, образец | писать хук | есть | **хук `post-install` RAUC → `VarSeeder`** |
| Критерии подтверждения | писать | `confirm.py` | **`confirm.py` → `rauc status mark-good`** |
| Испытано | нет | на файлах и образе диска | части — да; связка — нет |

Рекомендация: **C**. Причины: проверенная логика слотов, `/var` и критериев не теряется; модель доверия X.509 с CRL и `compatible` — у RAUC; один источник решений. **Не допускается два менеджера A/B одновременно**: dev-агент (`sheregesh-ota-agent`, только dev-образ, разрешение для серийного номера) — инструмент лаборатории до S5; в выпускном образе — только RAUC; общие модули (`slots.py`, `confirm.py`, `VarSeeder`, `sheregesh-health`) не принимают решений сами — их вызывает тот, кто решает (агент сейчас, RAUC потом). Модель `model.py` при варианте C перестаёт быть источником истины — им становится статус RAUC.

|---|---|---|---|

## 6. Аварийное восстановление и аппаратный watchdog

Факты: BCM2835 watchdog есть (`/dev/watchdog0`, «Broadcom BCM2835 Watchdog timer», состояние inactive), systemd его не использует (`RuntimeWatchdogUSec=0`, `RebootWatchdogUSec=10min` — только при перезагрузке). tryboot однократен: флаг пробной загрузки живёт до первого сброса.

| Отказ на пробной загрузке | Что происходит сейчас (watchdog выкл.) | С аппаратным watchdog (RuntimeWatchdogSec) |
|---|---|---|
| Ошибка приложения | systemd перезапускает службу (WatchdogSec приложения, лимит перезапусков); критерии подтверждения FAIL (`unit.*` с перезапусками) → не подтверждается; `ota-abort` по SSH → обычная перезагрузка → прежний слот | то же |
| Зависание systemd (PID 1) | SSH, скорее всего, нет; плата висит до выключения питания; после включения — прежний слот | сброс BCM2835 через RuntimeWatchdogSec → прежний слот без человека |
| Зависание ядра (до или после старта systemd) | висит до выключения питания; затем прежний слот | после старта systemd — сброс → прежний слот; **до** старта systemd watchdog ещё не взведён — человек |
| Нет SSH (сеть не поднялась) | `ota-abort` невозможен; критерий ssh не PASS → подтвердить нельзя; выключение питания → прежний слот | не помогает (система «жива» для watchdog) |
| Повреждённая новая система | запись проверена повторным чтением; если загрузка невозможна — прошивка/ядро не стартуют → выключение питания → прежний слот | см. «зависание ядра» |
| Подтверждён плохой слот | основной уже B: выключение питания не помогает | цикл «загрузка → зависание → сброс» без конца |

Восстановление доступа: (1) пока слот не подтверждён — выключить и включить питание; (2) после подтверждения — на Mac (картридер) на FAT-разделе `bootconfig` в `autoboot.txt` выставить `[all] boot_partition=2` → загрузится A; (3) исходная microSD платы или повторная запись образа `57e8fe4`/`8fd50b4` с Mac (`flash_sd.py`) — затем роли и ключи заново.

Дополнительные риски включения watchdog: ложные сбросы при долгой блокировке PID 1 (запись больших файлов, медленная microSD); сброс во время записи на microSD (ext4 с журналом, `commit=60`; `autoboot.txt` пишется атомарно); бесконечный цикл на подтверждённом плохом слоте; сложнее отладка. Рекомендация: включать (RuntimeWatchdogSec ≈ 30–60 с) **только** после отдельного испытания на pi2 с человеком у платы, на подтверждённом рабочем слоте, и отдельным решением.

## 7. Критерии подтверждения нового слота (`software/sheregesh/update/confirm.py`)

Агент вызывает их на пробной загрузке перед mark-good; любой обязательный не PASS → слот **не** подтверждается (модель: повтор tryboot или откат). Отпечатки снимаются при установке на рабочем слоте.

| Критерий | pi1 (console) | pi2 (remote) |
|---|---|---|
| `slot`: активен целевой слот, идёт пробная загрузка | ✔ | ✔ |
| `version`: `build.json` = версия манифеста | ✔ | ✔ |
| `persistent`: rw, `/home` и `/etc/ssh` с persistent | ✔ | ✔ |
| `same.*`: роль, machine-id, ключ и сертификат устройства, `link.json`, ключ хоста SSH, `authorized_keys` | ✔ | ✔ |
| `unit.ssh`, `unit.sheregesh-ota.socket` active | ✔ | ✔ |
| службы роли active **без перезапусков** (Type=notify: active = READY; watchdog не сработал) | `sheregesh-console` | `sheregesh-remote-net` |
| `failed-units`: нет | ✔ | ✔ |
| `uptime` ≥ 90 с (WatchdogSec служб успел бы сработать) | ✔ | ✔ |
| `health` verdict PASS; `health.network`: `config.link`, `link.state`, `certs.*` = PASS (не SKIP) | ✔ | ✔ |
| `mtls` | пульт: `connected`, TLSv1.3 | блок: сеанс с пультом |
| `video` (стенд S3.1-VIDEO) | `remote-tls`, `playing`, ≥ 25 к/с | видеосервер TLS на 7444 |

Испытано: `tests/unit/test_ota_s32.py` — 10 вариантов отказа каждого критерия → `FAILED`, основной слот не меняется; все PASS → `COMMITTED`; для блока не требуется пульт.

## 8. План первого аппаратного испытания OTA (только pi2; pi1 не обновляется)

Предусловия (STOP, если не выполнено): решения владельца 1–3 (раздел 9); человек у pi2 с доступом к питанию; Mac с картридером; исходная microSD pi2 под рукой; pi1 работает, канал и видео PASS.

| Шаг | Действие | Контрольная точка / GO | STOP |
|---|---|---|---|
| 0 | Снимок «до»: `shdeploy status/ota-status pi2`, хеши `authorized_keys`, `~/.local/share/sheregesh/link/*`, `link.json`, `/etc/ssh/*.pub`, `machine-id`, `autoboot.txt`; `check_link`, `check_video_link` (session, stream) | всё PASS | любой FAIL |
| 1 | **Запись слота B** (`shdeploy ota-install pi2 --payload …shota`) — *решение владельца 1* | `INSTALLED`; A и `autoboot.txt` прежние; службы не перезапускались; канал и видео работают | FAILED/REJECTED → разбор, без tryboot |
| 2 | **Разрешение переключения** (`shdeploy ota-enable pi2`) — *решение 2* | `switching: разрешено для 100000009d497e91` | — |
| 3 | **Пробная загрузка** (`shdeploy ota-tryboot pi2`) — *решение 3* | плата вернулась по SSH в слот B (`tryboot_now`), `HEALTH_PENDING`; `var-seed` отработал; pi1 переподключилась | нет SSH 5 мин → **выключить/включить питание** → A; `ota-abort` |
| 4 | Проверки на B: `ota-status`, критерии (сухой прогон `confirm` нет — смотреть `checks` в ответе), `check_link`, `check_video_link`, `systemctl stop sheregesh-console` → `inactive` (app-stop) | все критерии PASS | любой FAIL → `ota-abort` (обычная перезагрузка → A) |
| 5 | **Подтверждение** (`shdeploy ota-confirm pi2`) — *решение 4* | `COMMITTED`, `autoboot.txt` `[all]=3`; после `systemctl reboot` — снова B | FAIL → слот не подтверждается, `ota-abort` |
| 6 | Итог: снимок «после», сравнение хешей, DEV deploy на новом слоте (`shdeploy deploy pi2` → OK), `ota-disable pi2` | хеши совпадают, deploy OK | расхождение — разбор |

Отключение питания как испытание не выполняется; выключение/включение питания — только как средство восстановления при зависании (с решением владельца на месте).

## 9. Решения, требующие разрешения владельца

1. Записать неактивный слот B pi2 потоком `0.1.1792857986` (без переключения).
2. Внести подписанное разрешение переключения слотов для pi2 (`ota-enable`).
3. Выполнить пробную загрузку pi2 (`ota-tryboot`) — с человеком у платы.
4. Подтвердить слот B pi2 (`ota-confirm`) по итогам критериев.
5. Утвердить ADR-0009 (рекомендуется C) и ADR-0010.
6. Аппаратный watchdog: включать ли и когда (отдельное испытание).
7. AUD-014 для dev-пути (отзыв подписей).
8. pi1 — только после итогов pi2.
