# Этап A-4: обрыв потока и потеря управления по событию, службы по D-Bus — на стенде

**Дата:** 2026-10-31 · **Выпуск:** DEV `0.1.0~dev0+gea81fb6` (код `14eb957`) на обеих платах поверх образа
`44f5c21` · **Аренда:** `dev-ea81fb6` · **Полномочия:** владелец в чате — «Да, раскатывай». **Источник видео:** HDMI
devbox → MS2130 → pi2, 1280×720@60.

## Видео: обрыв потока и потеря управления

| Сценарий | Что делается | Результат | Критерий |
|---|---|---|---|
| stream-loss (REQ-SW-002 п. 3) | SIGSTOP `sheregesh-video-tx` блока 6 с, управление живо (`connected`) | «нет видео» **1,523 с**, видео снова **0,774 с** после возобновления; tx без перезапуска | ≤ 3 с / ≤ 10 с — PASS |
| ctl-loss | SIGSTOP `sheregesh-remote-net` 8 с, поток SRTP идёт | видео выключено **2,745 с** (тайм-аут heartbeat 3 с), снова **1,733 с** в новом сеансе SRTP | ≤ 4 с / ≤ 10 с — PASS |

Оба времени — по событию: часы блока непосредственно перед `kill` и метка смены состояния видео пульта
(`video.state_at`), часы плат синхронизированы (time-sync). Прежний замер опросом `ui-state.json` раз в 1 с давал
верхнюю оценку и «границу» 2,7–3,2 с: при SRTP он фактически мерил тайм-аут heartbeat — открытая проверка снята.

Полная проба видео: session, stream, resources, telemetry, no-plain, stream-loss, ctl-loss, restart, leftovers — PASS;
**latency — FAIL в 1 из 4 прогонов** при задержке в норме (p50 43,7–44,2 мс, p95 46,3–46,8 мс): отсчётов 24 / 239 /
103 / 29 при пороге > 50. Причина — служба rx очищала окно отсчётов при каждом `set-clock-offset`, а пульт
повторяет его каждые 5 с: число отсчётов зависело от момента чтения. Дефект прежний, не этого выпуска; исправлен в
`b2d50d4` (сброс только при изменении смещения > 1 мс), на платы ещё не раскатан. Связь `check_link` — 10/10.

## После исправления `b2d50d4` (DEV `0.1.0~dev0+g6ae97ee`, аренда `dev-6ae97ee`, «Да, раскатывай»)

- **latency:** 5 прогонов подряд — PASS, в каждом полное окно 600 отсчётов; p50 43,6–43,8 мс, p95 45,8–46,3 мс,
  max 53,0–54,8 мс.
- **Полная проба видео 10/10, связь 10/10.**
- **Проба ctl-loss сразу после stream-loss** в одном прогоне показала «нет видео» 0,0 с: видео ненадолго играло и
  сменило состояние до сигнала, метка state_at была старше сигнала. Вердикт (по выключению 2,92 с) не затронут, но
  значение недостоверно. Проба исправлена: перед сигналом — устойчивое «playing» ≥ 2 с с той же меткой, метка раньше
  сигнала — ERROR, а не 0. Три повтора обоих сценариев после исправления:

| Прогон | stream-loss: нет видео / возврат, с | ctl-loss: выключено / возврат, с |
|---|---|---|
| 1 | 1,540 / 0,515 | 2,910 / 1,188 |
| 2 | 1,551 / 0,745 | 2,311 / 1,423 |
| 3 | 1,518 / 0,706 | 2,372 / 1,623 |

«Нет видео» при обрыве потока ≈ 1,5 с — порог пульта `NO_VIDEO_AFTER_S` плюс такт; выключение по потере управления —
тайм-аут heartbeat 3 с от последнего принятого heartbeat (2,3–2,9 с от сигнала).
