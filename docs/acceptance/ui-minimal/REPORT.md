# UI Minimal — интерфейс пульта «видео на весь экран»: реализация и приёмка

- **Дата:** 2026-10-26. **Стенд:** pi1 (пульт, 192.168.1.92), pi2 (удалённый блок, 192.168.1.171), видео pi2 → pi1
  (синтетика 1280×720, 30 к/с). **Дисплея на pi1 нет** (HDMI-A-1/2 disconnected): окно рабочего пульта не
  отрисовывается, поэтому отрисовка измерена отдельным экземпляром пульта на GPU pi1 (см. «Нагрузка»).
- **Выпуск:** DEV deploy только на pi1 (ветка `ui/minimal`); образ, OTA, слоты, протокол, видеотракт pi2, CRSF не
  менялись. pi2 не переустанавливался.

## Что сделано

- `MainMinimal.qml`: строка состояния 28 px (база 1280×800), поле видео, нижнее меню 44 px (5 кнопок, около 7 мм под
  палец на 10,1"); на 1920×1200 всё ×1,5. Поле видео — 728 из 800 строк (91 %); кадр 16:9 занимает 720 строк, то есть
  меню 44 вместо 30 px кадр не уменьшает.
- Строка состояния: **УПРАВЛЕНИЕ** первым (IDLE/ACTIVE/FAILSAFE, передача, выход none/neutral/live), БЛОК,
  ВИДЕО (вход, к/с), ВВОД (аппаратура USB), МОДУЛЬ (эмулятор — SIM), справа LAB и общее предупреждение. Читает backend
  4 раза в секунду, а не на каждое изменение стиков.
- Разделы — панель справа (≤ 32 % ширины, центр кадра виден), без затемнения; закрытие: ×, тап по видео, Esc, та же
  кнопка; F1…F5 без сенсора. Панели создаются один раз в фоне и дальше только показываются.
- «Подробно» — прежние страницы (видео, управление, модуль, события, журналы, настройки, питание, сведения) на месте
  видео; недоступно, пока команды идут на модуль (выход live), и закрывается, если выход стал live.
- «Нет кадров» и «нет связи с блоком» — разные сообщения поверх поля; прежний кадр не показывается.
- «Система»: выпуск и предыдущий, OTA и слоты — только чтение (`sheregesh-ota-client status`, `sheregesh-deployd
  status` в фоновом потоке, не чаще раза в 30 с, `nice`); опасные действия — прежними страницами с их подтверждениями.
- Видео (общее для обоих интерфейсов): кадр рисуется в текстуру своего размера (640×360), растягивает сцена на GPU;
  поля заливаются только вокруг кадра; кадры читаются из трубы gst целиком (`readinto`, труба 1 МиБ) без копий.
- Прежний интерфейс вкладок оставлен: `SHEREGESH_UI=classic` или файл `~/.config/sheregesh/ui-layout` со словом
  `classic` (перезапуск пульта). Служба и ручной запуск — Minimal.

## Нагрузка

Рабочий пульт на pi1 без дисплея (`tools/probe/ui_perf.py`, 60 с, видео pi2 30 к/с; окно не рисуется):

| | CPU пульта, % ядра | RSS пульта | gst |
|---|---|---|---|
| до (вкладки, `perf-before.json`) | 36,5 | 214 МБ | 27,7 % |
| после (Minimal, `perf-after.json`) | 23,9 | 202 МБ | 27,6 % |

Отрисовка на GPU pi1 (`tools/probe/ui_bench.py`): отдельный экземпляр пульта под cage с виртуальным выходом
(рендер v3d, 1280×720), локальное синтетическое видео, 40–60 с. Стенд нагружен сильнее рабочего режима: локальный
кодировщик gst ~135 % ядра плюс рабочий пульт и его декодер — абсолютные к/с ниже 30, сравнение — при равных условиях.

| | CPU пульта | RSS | к/с окна | к/с видео (мин.) | открытие раздела |
|---|---|---|---|---|---|
| вкладки, страница «Видео», прежний код | 97,3 % | 196 МБ | 18,6–20,8 | 16 | — |
| вкладки, «Главная», прежний код | 62,3 % | 194 МБ | 21,6–25,4 | 17 | — |
| Minimal, покой | 60,0 % | 182 МБ | 26,2–28,4 | 23 | — |
| Minimal, разделы каждые 2 с | 61,9 % | 183 МБ | 25,0–28,4 | 18 | 23–84 мс |

- Навигация добавляет ~2 % ядра; памяти Minimal требует меньше прежнего (−12…−14 МБ), а не больше.
- Профиль до правок: отрисовка кадра ~6 мс/кадр (масштабирование и полная заливка на CPU), копия кадра 2,2 мс,
  чтение трубы мелкими порциями. После: `drawImage` ~2 мс/кадр (остаток — преобразование RGBx → ARGB32).
- Единственная просадка показа видео при навигации (до 18 к/с на перегруженном стенде) — раз в 30 с при обновлении
  сведений «Системы» (две Python-команды); в рабочем режиме (аппаратный декодер, без локального кодировщика) запас есть.

## Камера RTSP (shcam, Raspberry Pi 5 + IMX477)

- **Две платы, 30 с** (`perf-shcam.json`): pi2 переключён на `rtsp:1` «shcam Pi5 IMX477» через сокет пульта
  (тот же выбор, что в разделе «Видео»): ok, строка состояния «RTSP · 28 к/с», декодер pi1 30 к/с (минимум за срез),
  пульт 25,0 % ядра, gst 27,7 %, RSS 198 МБ (на синтетике 23,9 % / 202 МБ). После среза — обратно `synthetic`.
- **Снимки с картинкой камеры** `screens-shcam/` — тестовый экземпляр Minimal на GPU pi1, RTSP камеры напрямую на
  pi1 (`ui_bench.py --rtsp`), не через pi2: строка «Управление» поэтому «нет связи». Камера была не в фокусе; к/с на
  снимках занижены самим снимком окна (grabWindow), нагрузку этого прогона не используем.

## Видео: разрешение, формат, отклик (`video-matrix/`)

Стенд на GPU pi1 (`ui_bench.py --rtsp`), камера shcam (H.264 1280×720, 30 к/с) напрямую, по 30 с на вариант.
Задержка — внутри пульта: кадр получен из gst → кадр на экране (frameSwapped).

| Кадр на пульте | Формат, конвертация | Показ | Пульт CPU | gst CPU | к/с | Задержка p50 / p95 |
|---|---|---|---|---|---|---|
| 640×360 | RGBx, videoconvert | таймер 33 мс (было) | 40,7 % | 32,0 % | 28–32 | 15,1 / 31,9 мс |
| 640×360 | BGRx, videoconvert | таймер | 46,6 % | 29,0 % | 28–32 | 20,5 / 33,1 мс |
| 640×360 | BGRx, v4l2convert (ISP) | таймер | 46,0 % | 37,8 % | 28–32 | 18,2 / 32,4 мс |
| 640×360 | BGRx, v4l2convert | по приходу | 39,4 % | 36,7 % | 30–34 | 6,0 / 11,3 мс |
| **640×360** | **RGBx, videoconvert** | **по приходу (стало)** | **33,0 %** | **27,7 %** | **30–34** | **5,4 / 8,8 мс** |
| 960×540 | BGRx, v4l2convert | по приходу | 87,2 % | 67,7 % | 30–33 | 15,8 / 21,5 мс |
| 1280×720 | BGRx, v4l2convert | по приходу | 111,6 % | 77,6 % | 21–23 | 30,9 / 37,7 мс |
| 1280×720 | RGBx, videoconvert | по приходу | 64,8 % | 95,8 % | 12–15 | 28,5 / 46,0 мс |

- Выбрано: 640×360, RGBx, программная конвертация (как было), кадр — на экран сразу по приходу (`FRAME_WAKE`).
  Отклик пульта в 3 раза лучше, CPU меньше; конвейер gst и протокол не менялись.
- 1280×720 Pi 4 в этом тракте (кадр через Python) не держит 30 к/с; 960×540 держит ценой вдвое большей нагрузки —
  кандидат на режим «детально» по кнопке. Полное качество без потерь отклика — только путь кадра мимо Python
  (gst → текстура GPU), это новый образ (пакеты) и отдельная работа.
- BGRx и аппаратная v4l2convert на 640×360 выигрыша не дают.

## Не проверено / ограничения

- **Снимки рабочего пульта и время открытия на нём** — нет дисплея на pi1. Снимки `screens-pi1/` — с GPU pi1, но
  тестового экземпляра (локальная синтетика, без блока: «нет связи» в строке управления); `screens-local/` —
  offscreen на рабочей станции с эмулятором блока. Подключить экран → `{"cmd": "ui", "op": "grab"}` в сокет пульта.
  Без дисплея команда отвечает unsupported (первая версия ждала кадр, и watchdog перезапустил пульт — исправлено).
- Сенсор, физический размер элементов на 10,1", аппаратура Boxer на pi1 (сейчас не подключена) — не проверены.
- Задержка видео «стекло-стекло» не измерялась.
- Приёмка S6–S8 на платах читает тексты страниц вкладок: перед прогоном — `classic` в `~/.config/sheregesh/ui-layout`
  на pi1 и перезапуск пульта (учитывать StartLimitBurst 5/300 с).
- Видео декодируется в 640×360 и растягивается на весь экран; повышение разрешения — отдельное решение (нагрузка
  трубы и отрисовки), как и переход на текстуру BGRx без преобразования.

## Цикл разработки интерфейса

1. Правка QML → `python3 tools/dev/minimal_shots.py DIR [--quick]` (снимки 1280×800/1920×1200, ~7 с; плата не нужна).
2. `pytest tests/gui/test_gui_minimal.py` (~26 с).
3. Коммит в рабочую ветку (без push) → `python3 tools/deploy/shdeploy.py deploy pi1 --host 192.168.1.92` (~50 с,
   подписанный выпуск, откат `rollback`). Не больше 4–5 выкладок за 5 минут — лимит перезапусков службы.
4. Нагрузка на GPU платы: `python3 tools/probe/ui_bench.py --layout minimal --navigate [--grab DIR]`.
