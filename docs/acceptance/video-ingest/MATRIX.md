# VIDEO INGEST — матрица требований к видеовходу (QA)

Ветка `qa/video-ingest` (база `v2` 43ea9a9), 2026-10-25. Это не приёмка требований: испытания Must остаются
NOT TESTED, релизный гейт REQ-REL-001 — NO-GO. Требования и статусы ADR здесь не меняются.

Источник порогов — только SRS Rev. B (`docs/srs/SHEREGESH-SRS-1.0.md`) и `docs/requirements/requirements.json`.
Где числа нет, стоит «измерять, без критерия». Пороги, перенесённые на устройство захвата по аналогии, помечены
**«по аналогии»**: SRS их для захвата не устанавливает.

## 1. Что говорит SRS о видеовходе

Поиск по `docs/srs/`, `docs/requirements/`, `tools/reqs/`: UVC, CVBS, RTSP, HDMI-захват, «камера», «видеоисточник» —
**0 требований**. HDMI встречается только как выход на дисплей (REQ-P-002). Объём 1.0 — «отображение синтетического
видеопотока» (SRS §1). Все требования с видео:

- REQ-SW-002 — синтетический поток;
- REQ-R-007 и REQ-PWR-002 — частота синтетического потока под нагрузкой и на батарее;
- REQ-UI-003 — через запись каталога `VIDEO-LOST`;
- REQ-SYS-003 и REQ-UI-008 — ограничения на внешние источники в приёмке.

Отсюда:
1. Устройство захвата — лабораторная функция S3.3 (`docs/architecture/S3.3-universal-video-input.md`) вне SRS 1.0.
   Его испытания (HW-PLAN) дают инженерный вывод, а не PASS требования.
2. Для захвата прямо применимы только **регрессионные** требования: синтетический путь не должен деградировать —
   и REQ-UI-003 для `VIDEO-LOST`.
3. Если владелец хочет приёмку захвата, нужно требование с порогами (CHG к SRS). Это решение владельца, не QA (§4).

### Что проверяется только на стенде (и почему)

| Проверка | Почему не автотестом | Шаг |
|---|---|---|
| VID:PID, драйвер ядра, модуль в образе | подставное дерево sysfs повторяет только известные структуры | P3, D1, D2 |
| Фактические форматы, режимы, к/с | описание продавца и таблицы id — гипотеза | D2, D3 |
| Поведение без входного сигнала (кадры прекращаются / поле / повтор) | зависит от микросхемы и прошивки | D4 |
| Отображение на пульте реального кадра захвата | рендеринг QML без дисплея на pi1 с настоящим потоком | D3v |
| Время «нет видео» и восстановления при реальном USB-отключении | ядро, udev, повторная нумерация `/dev/videoN` | D6 |
| Задержка | нужен реальный источник с часами | HW-PLAN §3, только оценка |

## 3. Пороги — сводка

| Порог | Значение | Источник | Как применяется к захвату |
|---|---|---|---|
| «Нет видео» | ≤ 3 с | REQ-SW-002 п.3 | по аналогии (D5, D6) |
| Код, текст, действия неисправности | ≤ 3 с | REQ-UI-003 п.2 | прямо для `VIDEO-LOST` (D5, D6) |
| Восстановление видео | ≤ 10 с после возобновления | REQ-SW-002 п.3 | по аналогии (D4–D6) |
| Частота | ≥ 29 к/с за 30 мин, потери ≤ 1 % | REQ-SW-002 п.2 | не применяется; D3 — измерено, без критерия |
| Частота под нагрузкой / на батарее | ≥ 25 к/с | REQ-R-007 п.2, REQ-PWR-002 п.3 | не применяется (синтетический поток) |
| Задержка | нет в SRS | — | измерено, без критерия |

Погрешность замера по `ui-state.json`: ≈ +1,3 с в сторону завышения, консервативно для PASS (`../e2e/MATRIX.md` §2).

## 4. Открытые вопросы владельцу

1. Нужна ли приёмка захвата как требования (CHG к SRS: класс устройств, режимы, пороги к/с, «нет сигнала»), или это
   лабораторная функция без приёмки?
2. Где источник в целевой схеме — блок (задание спринта) или пульт (S3.3, локальный вход)?
3. Аналоговые захваты (`usbtv` / `em28xx`) ПО v2 не принимает (только `uvcvideo`), а режимы PAL/NTSC не входят
   в схему конфигурации. Поддерживать ли их (задача B) — решение владельца.
