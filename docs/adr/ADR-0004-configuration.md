# ADR-0004. Конфигурации: атомарные ревизии, подтверждение, откат, резервирование

- **Статус:** Принято (TL-002), 2026-10-22
- **Затронутые требования:** REQ-CFG-001…CFG-009, UPD-004, REC-001, SW-005, SYS-009

## Решение

**Формат:** YAML (только `safe_load`) с JSON Schema (draft 2020-12), по одному файлу на профиль. Схема версионируется вместе с ПО, публикуется в репозитории и устанавливается в образ (CFG-001). Валидатор возвращает путь к полю и класс ошибки.

**Хранение** (раздел data, на обоих устройствах одна и та же библиотека `sheregesh.config`):

```text
/data/config/
  revisions/<rev-id>/        неизменяемый каталог: *.yaml + MANIFEST.json
                             (sha256 файлов, версия схемы, родитель, время, автор, причина)
  state.json                 {current, confirmed, pending|null, snapshots:[...], slots:{A,B}}
  quarantine/<rev-id>/       неуспешные ревизии (для диагностики, CFG-005)
/data/secrets/               секреты отдельно от ревизий (CFG-007) — в резервные копии не входят
```

**Применение новой ревизии (CFG-002…004):**
1. Валидация всех файлов набора по схеме. При ошибке активная ревизия не меняется.
2. Запись в `revisions/.tmp-<id>/`, `fsync` файлов и каталога, переименование в `revisions/<id>/`, `fsync` родительского каталога.
3. Автоснимок: текущая confirmed-ревизия помечается в `snapshots` (CFG-009). Хранятся 3 последних снимка; подтверждённые ревизии, на которые ссылаются слоты, не удаляются.
4. `state.json` переписывается атомарно (временный файл + `fsync` + `rename`): `pending = <id>`, `current = <id>`. Это единственная точка переключения всего набора (CFG-003).
5. Затронутые службы перечитывают конфигурацию и выполняют health-check (перечень проверок указан в схеме для каждого раздела).
6. Успех: `confirmed = <id>`, `pending = null`. Провал или таймаут 60 с: `current = confirmed`, ревизия переносится в `quarantine`, событие идёт в журнал и GUI.

**Загрузка (CFG-005):** если в `state.json` есть `pending`, ревизия переносится в `quarantine`, и `current = confirmed`. Неподтверждённая ревизия никогда не активируется автоматически.

**Связь со слотами A/B (CFG-006, UPD-004):** при подтверждении слот, с которого загружена система, запоминает `slots[<slot>] = confirmed`. После отката ОС на слот X активируется `slots[X]`, а более новая ревизия остаётся в `revisions/` и доступна для просмотра.

**Резервирование на USB (CFG-008):** архив `tar` (каталог ревизии + манифест + версия схемы + тип устройства + SHA-256), без `/data/secrets`. Восстановление проходит в порядке:
- проверка манифеста и совместимости;
- явное подтверждение пользователя;
- создание новой ревизии из архива;
- обычный путь применения (шаги 1–6).

Для удалённого блока: пульт получает архив через агент и пишет его на свой USB; восстановление идёт в обратном направлении.

**Удалённый блок:** пульт передаёт агенту полный набор новой ревизии (ADR-0007). Агент проверяет её своей копией библиотеки и схемы, применяет и сообщает результат. Пульт не пишет файлы удалённого блока напрямую.

**Тесты:** инжекция сбоя (исключение или `os._exit`) в каждой точке `fsync`/`rename` — в CI на tmpfs и ext4 через loop-устройство (L3). Отключение питания сетевым выключателем — на стенде (L4).

## Отклонённые варианты
- **git как хранилище ревизий:** лишняя зависимость; атомарность всё равно определяется указателем.
- **Указатель через символическую ссылку:** допустим, но `state.json` хранит ещё pending, snapshots и slots одной атомарной записью.
- **SQLite:** конфигурация должна оставаться читаемыми YAML-файлами (CFG-001).
