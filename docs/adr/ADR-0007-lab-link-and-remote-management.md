# ADR-0007. Лабораторный обмен между устройствами и управление удалённым блоком

- **Статус:** Принято (TL-002, D3), 2026-10-22
- **Затронутые требования:** REQ-SYS-002, SYS-007, SYS-008, SW-002, SW-003, SW-004, UI-004, UI-006, CFG-008, REC-002, REL-004, REL-005

## Решение

**Канал:** прямой Ethernet-кабель в изолированном стенде. Статические адреса: пульт 192.168.77.1/24, удалённый блок 192.168.77.2/24; без шлюза и DNS. Сетевой коммутатор не обязателен.

**Протокол управления** `SHRG-LAB`. Описание — `docs/protocol/PROTOCOL.md`, создаётся на этапе S1.
- TCP, порт 7700. Удалённый блок — сервер (агент), пульт — клиент.
- Сообщения: JSON UTF-8, по одному на строку: `{"proto": "1.0", "type", "seq", "ts", "body"}`.
- Рукопожатие `hello` в обе стороны:
  - версия протокола MAJOR.MINOR, версия ПО (SemVer), HW-версия, тип и ID устройства;
  - **правило совместимости (CHG-012):** одинаковый поддерживаемый MAJOR, MINOR второй стороны не ниже минимума матрицы, ПО не в списке отклонённых, допустимая HW-версия; сессия работает на MAJOR.min(MINOR); сообщения новее версии сессии не исполняются. Иначе отказ с сообщением; после отказа разрешены только `hello` и `bye`.
  - **сеанс принадлежит соединению (уточнение 2026-10-29):** согласованная версия — свойство конкретного соединения.
    Новое соединение начинает без сеанса; прикладные команды (`rc`, `module-cmd`, `video-select`, `video-key-ack`,
    `video-fallback`, `video-renew`, `ack`) исполняются только после успешного `hello` этого же соединения, пока оно
    текущее; проверка повторяется после каждого `await` перед изменением общего состояния. Сообщения, `bye` и задачи
    отправки заменённого или закрытого соединения не закрывают новое соединение и не меняют его версию, видео и выход
    управления. Несовместимый `hello` сеанса не даёт. mTLS-аутентификация соединения остаётся прежней.
  - Матрица `software/sheregesh/compat-matrix.yaml` задаёт поддерживаемые версии и ограничения ПО/HW (SYS-008).
- Heartbeat раз в 1 с. При отсутствии 3 с — состояние «нет связи» (критерий ≤ 5 с). Клиент переподключается с задержкой 1 → 2 → 4 с, но не реже раза в 4 с (критерий восстановления ≤ 10 с).
- `seq` монотонен; приёмник считает пропуски и нарушения порядка (SYS-002, link-test).
- Объёмные передачи (бандл обновления, архив конфигурации, экспорт журналов) идут отдельным TCP-соединением: `{"size", "sha256"}`, затем данные; приёмник проверяет хеш.

**Команды агента** (D3 — всё управление удалённым блоком идёт через пульт):

| Команда | Изменяет состояние | Подтверждение на пульте (SYS-009) |
|---|---|---|
| `status.get`, `passport.get`, `services.get`, `power.get`, `thermal.get` | Нет | — |
| `config.get`, `config.apply`, `config.rollback`, `config.backup`, `config.restore` | `apply`, `rollback`, `restore` — да | Да |
| `logs.export` | Нет | — |
| `update.install` | Да | Да |
| `power.shutdown`, `power.reboot` | Да | Да |
| `indicator.test` | Нет (временно) | — |
| `devmode.enable` | Да | Да, плюс физическая кнопка пульта (UPD-005) |

Каждая изменяющая команда записывается в журналы обоих устройств с `seq` и результатом.

**Видео (SW-002):** RTP/UDP, H.264, 1280×720 @ 30 к/с, порт 5600, от удалённого блока к пульту; фиксированные caps. Источник — `videotestsrc` и аппаратный `v4l2h264enc`. На пульте есть локальный генератор для работы без удалённого блока.

**Индикатор удалённого блока (UI-004, D3):** RGB за световодом. Таблица состояний — `docs/ui/status-indicator.md`, создаётся на этапе S1. Базовые состояния: загрузка, норма, нет пульта, применение или обновление, безопасный режим, неисправность.

**Безопасность канала:** TLS 1.3 с взаимной аутентификацией устройств (TL-005, AUD-028). Обновления защищены независимо: удалённый блок сам проверяет подпись (ADR-0006).

**Команды управления:** протокол расширяется командами управления наземными платформами (D6). Набор команд, взведение, приоритет источников и поведение при потере связи определяет ADR канала управления.

## Отклонённые варианты
- **gRPC / protobuf:** тяжелее зависимости и отладка, выгоды при таком объёме нет.
- **MQTT:** нужен брокер — лишний компонент.
- **SSH как канал управления:** смешивает доступ разработчика и протокол продукта, хуже тестируется эмулятором.
- **mDNS-обнаружение:** не нужно при двух узлах со статическими адресами; при необходимости добавляется в MINOR.

## Реализация S1.5 (2026-10-23)

- Канал реализован между двумя процессами на `127.0.0.1` (`software/sheregesh/link/`, `software/remote/sheregesh_remote/`). Обе стороны отказываются работать не через loopback.
- Типы сообщений версии 1.0: `hello`, `heartbeat`, `status`, `event`, `error`, `bye`. Строка не длиннее 64 КиБ; проверяются поля `proto/type/seq/ts/body`; состояние второй стороны разбирается как недоверенные данные.
- В S1.5 команды агента из таблицы выше **не реализованы**: удалённый блок только сообщает синтетическое состояние, а от пульта принимает `hello` и `bye`. Остальные сообщения учитываются и не исполняются. Команды управления конфигурацией, обновлением и выключением блока появятся на этапе S5 с подтверждением на пульте.
- Пороги: «нет связи» — при отсутствии heartbeat дольше `heartbeat_timeout_s` (3 с); `PEER-SLOW` — при возрасте больше половины таймаута; после 10 повреждённых сообщений подряд соединение переустанавливается; переподключение — 0,5 → 1 → 2 → 4 с.

## Сетевой лабораторный профиль: mTLS (S3.1, 2026-10-23, TL-005)

Ограничение «аутентификации и шифрования в 1.0 нет» снимается для обмена между двумя физическими платами. Loopback-режим без TLS сохраняется только для разработки и тестов на одной плате.

- **Транспорт:** TLS 1.3 (только), взаимная аутентификация (`CERT_REQUIRED` с обеих сторон), доверие — только CA стенда (без системных корней), `VERIFY_X509_STRICT`.
- **Идентичность:** SAN URI `urn:sheregesh:<роль>:<серийный номер платы>`. Каждая сторона сверяет URI второй стороны с `peer_id` из `~/.config/sheregesh/link.json`. IP-адрес идентичностью не считается: адреса выдаёт DHCP, адрес второй стороны берётся из конфигурации или находится поиском в подсети, но соединение принимается только по сертификату.
- **Ключи:** EC P-256, создаются на самой плате (`sheregesh-link keygen`), права 0600, хранятся на разделе данных (`~/.local/share/sheregesh/link`), в Git, CI, образы и журналы не попадают. CSR подписывает тестовый CA стенда на машине владельца (`tools/lab-pki/labpki.py`), ключ CA — вне репозитория. Замена сертификата — повторный enroll (новый ключ, атомарная установка); отзыв — новый CA и повторное спаривание.
- **Ограничение доступа:** сервер (`sheregesh-remote-net`) не запускается без роли, ключа, сертификата и CA (условия systemd и проверка в приложении). Входящие: systemd `IPAddressAllow` — только loopback, частные и link-local сети; приложение — только подсеть интерфейса; затем TLS и URI. Не более 4 одновременных рукопожатий, таймаут 5 с, сообщения не длиннее 64 КиБ.
- **Протокол 1.1:** тип `ack` — подтверждение пультом heartbeat и диагностических событий (задержка и потери). Ничего не исполняет. Сессия с версией 1.0 работает без `ack` (CHG-012).
- **Состояния на пульте:** CONNECTED, RECONNECTING (связь потеряна менее 30 с назад, идут попытки), DISCONNECTED, AUTH FAILED (отказ TLS или чужой URI), INCOMPATIBLE.
- **Видео между платами** — отдельная подзадача S3.1-VIDEO: открытый UDP по общей сети не используется.

## Протокол 1.6: журнал и выключение блока с пульта (2026-11-01)

Из таблицы команд агента реализованы `logs.export` и `power.shutdown` (REQ-SW-001/005, REQ-UI-006; Smoke Test R5, R6).
Схемы — `software/sheregesh/link/remotecmd.py`, блок — `software/remote/sheregesh_remote/maintenance.py`.

- **Сообщения 1.6:**
  - `remote-cmd` (пульт → блок): `{"req", "op": "log-export" | "shutdown", "confirm": true}`. Без `confirm: true`
    выключение не исполняется (`bad-request`). Других операций нет, произвольных команд ОС тоже нет.
  - `remote-log` (блок → пульт): часть журнала `{"req", "part", "parts", "data"}`, base64 по 32 КиБ.
  - `remote-cmd-result` (блок → пульт): итог `ok | error | busy | bad-request`; для журнала ещё `name`, `size`,
    `sha256` и `parts`.
  - Сессия 1.5 этих сообщений не отправляет и не исполняет; пульт показывает «не поддерживается».
- **Журнал:**
  - Блок собирает `journalctl -b -u 'sheregesh-*'` за текущую загрузку, а в эмуляторе — журнал своего агента.
  - Секреты заменяются фильтром `sheregesh.redact`, общим с пультом.
  - Размер ограничен 2 МиБ: остаются последние записи.
  - Пульт собирает части по порядку, сверяет размер и SHA-256 и пишет файл на «USB» с `.sha256` рядом.
- **Отступление от правила «объёмные передачи — отдельным TCP-соединением»:** журнал идёт частями внутри того же
  сеанса mTLS.
  - Объём ограничен, а части меньше предела строки 64 КиБ.
  - Heartbeat и `status` чередуются с частями, так что сеанс не теряется. Сбор журнала идёт отдельной задачей и не
    задерживает приём `ack`.
  - Новый порт, правило межсетевого экрана и вторая аутентификация не нужны.
  - Бандл обновления сюда не относится: OTA остаётся по ADR-0006.
- **Выключение:**
  - После подтверждения оператора на пульте («Настройки» → «Выключить удалённый блок…», по умолчанию «Отмена»)
    агент запускает `sheregesh-remote-poweroff.service`. Юнит работает от root и только на роли remote; через 1 с
    он вызывает `systemctl --no-block poweroff`.
  - Правило polkit `54-sheregesh-remote-power.rules` разрешает `sheregesh-ui` только `start` этого юнита. Прав на
    `login1` и другие юниты оно не даёт.
  - Итог уходит пульту до остановки служб. Событие записывается в журналы обоих устройств: агент — в журнал
    службы блока, пульт — в журнал приложения и в журнал службы `sheregesh-console`.
  - Включение после выключения — только питанием: кнопки у блока нет, по REQ-UI-006 она не обязательна.
- **Режим разработчика блока (REQ-UPD-005):**
  - `remote-cmd` с `op: "dev-arm"` и `confirm: true` подаётся после диалога на пульте: «Настройки» → «Разрешить на
    удалённом блоке…».
  - Блок вызывает `sheregesh-ota-client dev-arm` из службы `sheregesh-remote-net`. Агент OTA сам проверяет, что
    вызывающий — служба устройства (SO_PEERCRED → cgroup).
  - Взвести режим по SSH по-прежнему нельзя.
- **Локальный канал пульта:** `{"cmd": "remote", …}` и `python3 -m sheregesh.link.remotectl log-export | shutdown
  --confirm` вызывают те же слоты, что кнопки. Smoke Test выключает блок только с флагом `--shutdown-remote` и
  последним пунктом.
