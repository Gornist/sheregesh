# ADR-0009. Единый механизм обновлений: RAUC + tryboot, разметка image-rota

- **Статус:** Предложено Tech Lead (S3.1, 2026-10-23), **ожидает утверждения владельцем**. Уточняет ADR-0006, не отменяет его.
- **Затронутые требования:** REQ-UPD-001…006, REC-001, REC-002, CFG-006
- **Связано:** ADR-0005 (подпись), ADR-0006 (A/B), S2-1/S2-BOOT (образ на image-rota), `software/sheregesh/update/model.py`

## Проблема

В образе одновременно присутствуют три механизма, каждый из которых может «решать» про слоты:

| Компонент | Что даёт | Ограничения для «Шерегеша» |
|---|---|---|
| **tryboot** (прошивка Pi 4) | Однократная загрузка другого раздела; без подтверждения — возврат на основной | Только механизм загрузки; решения об установке и подтверждении не принимает |
| **image-rota** (`rpi-image-gen`) | Разметка GPT A/B, привязка `/dev/disk/by-slot/{active,other}`, `rpi-slot-tryboot` (генерация `autoboot.txt`), персистентный раздел; пакет `<image>.update.tar.zst` | Пакет рассчитан на агент `rpi-connect-ota` (Raspberry Pi Connect): нужен облачный сервис и интернет, своя модель доверия — противоречит офлайн-работе и подписи по ADR-0005 |
| **RAUC** (ADR-0006) | Подписанные бандлы X.509 (CMS) с офлайн-проверкой по закреплённому keyring, `compatible`, статус слотов, `mark-good`/`mark-bad`, свой бэкенд загрузчика (`bootloader=custom`) | Нужен собственный бэкенд для tryboot (скрипт), сборка бандла из артефактов image-rota |

Два независимых установщика (RAUC и агент Connect) или ручной tryboot помимо RAUC создают конкурирующие источники истины о том, какой слот основной.

## Решение (предложение)

1. **RAUC — единственный компонент, принимающий решения** об установке, подтверждении и откате. Его бэкенд `custom` реализует операции через tryboot: «загрузить другой слот один раз» — `reboot "0 tryboot"` с `[tryboot] boot_partition=<other>`; «сделать основным» — запись `[all] boot_partition=<slot>` в `autoboot.txt` раздела `bootconfig` (та же логика, что в `rpi-slot-tryboot`).
2. **image-rota используется только как разметка и привязка слотов** (уже в образе S2-1). Агент `rpi-connect-ota` и Raspberry Pi Connect в образ не входят; пакет `.update.tar.zst` не используется — бандл RAUC собирается из тех же `system.ext4`/`boot.vfat`.
3. **`sheregesh-health` — единственный источник решения «новый слот здоров»**; `rauc status mark-good` вызывается только по его PASS (S5). На этапе S3.1 health-check работает в диагностическом режиме: mark-good, переключение слотов и перезагрузки не выполняет.
4. **Модель состояний** — `software/sheregesh/update/model.py`: IDLE → VERIFIED → INSTALLING → INSTALLED → TRYBOOT → HEALTH_PENDING → COMMITTED | ROLLED_BACK, FAILED. Инварианты: mark-good только после health PASS; основной слот меняется только в COMMITTED; не более 2 попыток загрузки нового слота (UPD-004); запись только в неактивный слот; откат возвращает и конфигурацию (свой `/var` у каждого слота). Модель испытана тестами без записи в загрузочные разделы (`tests/unit/test_update_model.py`).
5. Dev-режим (UPD-005/006, AUD-013) — тем же RAUC с локально внесённым ключом разработчика после решения владельца.

## Последствия

- Отступления от ADR-0006 нет: RAUC + tryboot без U-Boot сохраняются, уточнено распределение ролей. CHG не требуется.
- Работы S5: бэкенд `custom` для RAUC, `system.conf` со слотами по `/dev/disk/by-slot`, сборка подписанного бандла в CI (тестовый ключ), `sheregesh-health` → `mark-good`, испытание S2-5 (20 циклов tryboot, отключение питания — с отдельным оборудованием).

## Отклонённые варианты

- **Пакет image-rota + rpi-connect-ota:** облачная зависимость и интернет, модель доверия вне ADR-0005.
- **Только tryboot без RAUC:** нет проверки подписи бандла и учёта статуса слотов — пришлось бы писать свой установщик.
- **RAUC с U-Boot:** лишний загрузчик при штатном tryboot (ADR-0006).
