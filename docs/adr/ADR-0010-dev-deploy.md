# ADR-0010. Обновления лабораторных плат без перестановки microSD: DEV deploy и подготовка OTA

- **Статус:** Предложено (S3.1-DEPLOY, 2026-10-24), **ожидает утверждения владельцем**. Относится только к dev-образу (`sheregesh-lab-dev-pi4`); строгий и будущий выпускной образы механизм не содержат в рабочем виде.
- **Затронутые требования:** не меняет требования. Не является реализацией REQ-UPD-005 (там — физическое подтверждение на устройстве); это инструмент разработки, как SSH в dev-образе (ADR-0002).
- **Связано:** ADR-0002 (dev-доступ), ADR-0005 (подпись), ADR-0006/ADR-0009 (A/B, tryboot), `software/sheregesh/deploy/`, `software/sheregesh/update/{slots,ota}.py`, `tools/deploy/shdeploy.py`

## Проблема

Каждое изменение Python/QML сейчас требует сборки полного образа (~10 мин в CI) и физической перезаписи microSD на обеих платах. Владелец хочет обновлять платы по сети: приложение — быстро, систему — через A/B. При этом на платах нет root-доступа (вход `sheregesh-ui` по ключу, без sudo), корень только для чтения, а `polkit` разрешает лишь запуск/остановку четырёх служб и перезагрузку.

## Что можно сделать на текущих картах без записи (разведка)

| Путь | Вывод |
|---|---|
| Заменить код в `/usr/lib/sheregesh` | Невозможно: корень `ro`, у `sheregesh-ui` нет root |
| Записать неактивный слот (`/dev/mmcblk0p3`, `p5`) для OTA | Невозможно: блочные устройства только для root/disk |
| `reboot "0 tryboot"` (разрешено polkit) | Возможно, но слот B — побайтовая копия A; записать в него нечего |
| Файл `.pth` в `~/.local/lib/python3.13/site-packages` | **Технически возможно** для пульта и `remote-net` (работают от `sheregesh-ui`, Python читает пользовательские site-packages): код из домашнего каталога подмешивается в службу. **Отклонено:** нет проверки подписи и целостности, нет автоматического отката, не работает для `remote-emu` (DynamicUser), обходит «код только из ro-корня». Это дыра, а не механизм; в новом образе закрыта (`python3 -s` во всех командах `sheregesh-*`) |

**Следствие: нужна одна последняя физическая запись microSD на каждой плате** — образом, где уже есть всё ниже. Любой механизм, в котором подпись что-то значит и есть автоматический откат, требует компонента root (установщик), логики выбора кода в ro-корне (launcher), правила polkit и открытого ключа в ro `/etc`; ничего из этого без root на текущих картах не добавить. После этой записи приложение обновляется DEV deploy, система — OTA A/B (после отдельного разрешения), карты не вынимаются.

## Решение (предложение)

### 1. DEV deploy приложения

```
Mac: shdeploy deploy pi1
  git HEAD → пакет tar.xz (manifest.json: версия, коммит, compatible, SHA-256 каждого файла)
  ssh-keygen -Y sign (закрытый ключ только на Mac; пространство имён sheregesh-deploy)
  ssh sheregesh-ui@pi1: серийный номер сверяется → пакет и подпись в ~/.cache/sheregesh-deploy/incoming
  ssh sheregesh-ui@pi1: systemctl start sheregesh-deploy@install.service      ← polkit: только «start» этого юнита
Плата (root, код только из /usr):
  чтение incoming (O_NOFOLLOW, владелец sheregesh-ui, предел 32 МиБ) → подпись по /etc/sheregesh/deploy/allowed_signers
  → строгий разбор (только обычные файлы в каталогах приложения, без «..»/ссылок, SHA-256 каждого файла, compatible)
  → /var/lib/sheregesh-deploy/releases/<id> (root, 0755/0644, без байт-кода) → symlink current через rename(2)
  → перезапуск только служб роли: пульт — sheregesh-console; блок — sheregesh-remote-net; без роли — эмулятор и пульт
  → READY (Type=notify) и окно наблюдения 40 с (дольше WatchdogSec=20) без перезапусков
  → иначе current возвращается на прежний выпуск (или заводской код), службы перезапускаются: ROLLED_BACK
Старт службы: /usr/bin/sheregesh-console → python3 -I launcher.py (из /usr)
  current → проверка владельца root, SHA-256 всех файлов, отсутствия посторонних файлов → exec python3 -s -m модуль
  иначе (нет current, битый выпуск, не подтверждён до перезагрузки) → заводской /usr/lib/sheregesh
```

- **Модель привилегий.** `sheregesh-ui` может только положить файл в свой каталог и запустить один из трёх экземпляров `sheregesh-deploy@{install,rollback,factory}` (polkit: `verb == "start"`). Параметров, путей, команд и имён служб установщик извне не принимает. Присланный код от root не исполняется и не компилируется (аудит S3.1-DEPLOY: компилятор CPython от root на недоверенном входе исключён; Python компилирует выпуск в памяти в непривилегированной службе, 0,2 с на Pi 4); непроверенный `.pyc` в выпуске — отказ launcher; он работает в тех же непривилегированных службах, что и раньше (`sheregesh-ui`, DynamicUser эмулятора). Установщик, launcher, ретранслятор, `sheregesh-health`, `sheregesh-link` и агент OTA всегда работают из `/usr`. SSH от приложения не зависит.
- **Два фактора.** Ключ входа SSH даёт доступ, но не право установки: нужен ещё ключ подписи. Ключ подписи — отдельный (`~/.ssh/sheregesh-deploy`, переменная репозитория `SHEREGESH_DEPLOY_PUBKEY`). Без него или при совпадении с ключом входа dev-образ не собирается, а `verify.json` отмечает совпадение как FAIL.
- **Подпись — ssh-keygen -Y, а не X.509/RAUC.** OpenSSH уже есть в dev-образе и на Mac, ключ владельца уже существует, закрытый ключ не попадает ни в репозиторий, ни в CI, ни в образ. Выпускная подпись по ADR-0005 (корень + ключ выпуска) этим не заменяется.
- **Откат.** Автоматический — при невыходе в READY или падении в окне; ручной — `shdeploy rollback piN` (предыдущий выпуск) и `shdeploy factory piN` (заводской код образа). Сбой питания между переключением и подтверждением: launcher по `pending` с другим `boot_id` выбирает прежний выпуск, следующий запуск установщика отменяет переключение.
- **/var свой у каждого слота** (image-rota): выпуски DEV deploy привязаны к системе слота; после OTA новый слот стартует с кодом своего образа.
- **Не защищает от:** повторной установки старого подписанного выпуска владельцем ключей (откат версии в dev — функция); компрометации Mac владельца.

### 2. Подготовка OTA A/B (системные изменения)

Агент `sheregesh-ota` (root, сокет `/run/sheregesh-ota.sock` 0660 `root:sheregesh-ui`, Accept=yes; клиент `sheregesh-ota-client` в сеансе SSH):
- **install** — поток `SHRGOTA1`: подписанный манифест (пространство `sheregesh-ota`; `compatible` dev/строгий, разметка `image-rota-gpt-ab-1`, версия, SHA-256 сжатых и исходных образов) и образы `boot`/`system` в xz. Подпись проверяется до чтения образов. Активный слот определяется по `/dev/disk/by-slot`, меткам GPT, `mountinfo` и разделу из device-tree; расхождение — отказ. Запись — только в разделы неактивного слота (`O_EXCL`, проверка «не смонтирован»), затем fsync, сброс кэша и повторное чтение с проверкой SHA-256. `/persistent/slots/system_<неактивный>/var` пересоздаётся из `/var` нового образа (как при сборке image-rota), в него переносится конфигурация пульта `/var/lib/sheregesh` (REQ-CFG-006: у прежнего слота остаётся своя). Общие части persistent (`/home`, ключи и сертификаты связи, хост-ключи SSH, machine-id) не трогаются.
- **tryboot / confirm** — выключены, пока на плату не внесено **разрешение, подписанное владельцем для серийного номера этой платы** (`shdeploy ota-enable pi2`, пространство `sheregesh-ota-enable`). `tryboot` пишет `[tryboot] boot_partition` и делает `reboot "0 tryboot"`; `confirm` — только на пробной загрузке, только по `sheregesh-health` без FAIL, только по явной команде; он и есть mark-good (`[all] boot_partition`). Автоматического подтверждения и автоматической пробной загрузки нет.
- **Откат** — обычная перезагрузка (прошивка tryboot возвращает основной слот), `abort`, не более 2 попыток (REQ-UPD-004, модель `update/model.py`).
- Это лабораторный dev-путь. Выбор механизма для выпускного образа — ADR-0009 (дополнение S3.1-DEPLOY).

## Последствия

- Нужна одна запись microSD на каждой плате образом из этой ветки (dev-вариант). Дальше: `shdeploy deploy|rollback|factory|status`, `shdeploy ota-*`.
- Владельцу: утвердить ADR; отдельный ключ подписи и переменная `SHEREGESH_DEPLOY_PUBKEY` созданы 2026-10-24 (закрытый ключ — только на Mac владельца); решить, когда разрешить переключение слотов на pi2 для испытания.
- Остаточные риски и непроверенное — `docs/acceptance/s3.1-deploy/REPORT.md`.

## Отклонённые варианты

- **sudo/root по SSH для разработчика** — произвольное выполнение команд с повышенными привилегиями.
- **`.pth` в пользовательских site-packages** — см. разведку выше.
- **Overlay поверх `/usr`** — меняет модель ro-корня и SBOM всей системы ради кода приложения.
- **Сборка полного образа на каждое изменение** — то, от чего уходим; остаётся для системных изменений через OTA.
- **Пакет image-rota `.update.tar.zst` + rpi-connect-ota** — облачная зависимость (ADR-0009).


## Уточнение DEV deploy после ADR-0016 (2026-10-27)

Обновлённый установщик перезапускает `video-rx → console` для роли console и
`video-tx → remote-net` для remote. Standalone сохраняет эмулятор и пульт без сетевой видеослужбы.
Обе службы роли входят в окно наблюдения и повторный запуск при откате.
Отсутствующий video-юнит (`LoadState=not-found`) старого образа явно отмечается и пропускается;
ошибка загрузки или masked не считается отсутствием. ConditionPathExists обрабатывается как прежде.
Обёртки video-tx/rx в новом образе используют launcher DEV-выпуска.
Аппаратная проба сохраняет свежие строки launcher каждой применимой службы и сравнивает их с ожидаемым выпуском.

**Активация:** installer, обёртки и unit находятся в ro-образе. Изменение исходников или установка обычного
DEV-пакета сами по себе не исправляют существующий образ. Нужен новый образ и аппаратная приёмка install,
video-failure/rollback/factory с восстановлением потока; локальные тесты не заменяют её.
