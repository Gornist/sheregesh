# ADR-0011. Защищённый видеоканал между платами (S3.1-VIDEO)

**Статус:** заменено ADR-0016 (2026-10-30): видео между платами — только SRTP через службы sheregesh-video-tx/rx,
TLS-видеоканал (`videolink.py`, TCP 7444, `video-fallback` пульта) удалён из кода. Ниже — историческое решение
S3.1-VIDEO; требования не менялись.

## Контекст

Синтетическое видео (только `videotestsrc`) до S3.1 шло RTP/UDP через loopback одной платы (ADR-0003, ADR-0007). Для pi2 → pi1 нужен канал, который принимает только аутентифицированные устройства стенда, не выпускает незашифрованный RTP в общую LAN, не имеет обходного UDP при ошибке защиты, закрывается вместе с сеансом управления и не мешает heartbeat и телеметрии. Своя криптография запрещена. Системные пакеты образа `57e8fe4` менять нельзя без новой записи карт (корень только для чтения, OTA не активирована).

Проверено на обеих платах (2026-10-24): есть `srtpenc/srtpdec`, `dtlssrtpenc/dtlssrtpdec` (libsrtp2 2.7.0, gst-plugins-bad 1.26.2), `v4l2h264enc/v4l2h264dec`, `rtpstreampay/rtpstreamdepay`; привязок GStreamer для Python (`gi`) **нет**; `/proc/<pid>/cmdline` читается всеми (0444).

## Варианты

**A. SRTP (ключ через канал mTLS) / DTLS-SRTP.** Сохраняет RTP/UDP и потери без блокировки по TCP. Но без `gi` ключ SRTP передаётся `srtpenc`/`srtpdec` только через командную строку `gst-launch` (свойство `key` / caps `srtp-key`) — его видит любой локальный процесс через `ps`. DTLS-SRTP требует обработки сигналов проверки сертификата второй стороны — снова привязки. `python3-gi` — системный пакет: новый образ и перезапись карт. Открывается UDP-порт пульта в LAN (пусть и с шифрованием).

**B. Отдельное соединение TLS 1.3 с взаимной аутентификацией (выбрано).** Тот же `ssl`, CA стенда, сертификаты устройств и проверка URI, что у проверенного канала управления (10/10 PASS), — без новых пакетов. Отдельный порт `video_port` (7444) и отдельные потоки: видео не блокирует heartbeat и телеметрию. Ключи сеанса — эфемерные ECDHE внутри процесса, в командные строки и журналы не попадают; каждое подключение — новое рукопожатие. Подложные или изменённые байты рвут соединение (AEAD). Недостаток — TCP: при потерях задержка растёт вместо выпадения кадров; на проводной лабораторной LAN это приемлемо, буферы ограничены (запись блокируется, генератор живого источника пропускает кадры).

## Решение

Вариант B, модуль `software/sheregesh/videolink.py`:

- блок: `videotestsrc → H.264 (v4l2h264enc) → rtph264pay → rtpstreampay → stdout` → `VideoServer` → TLS → пульт;
- пульт: TLS → `VideoClient` → stdin → `rtpstreamdepay → rtpjitterbuffer → v4l2h264dec → videoscale → RGBx 640×360` (`sheregesh_console.video`);
- **RTP не попадает ни в один сокет** — только каналы процессов на каждой плате и TLS между ними; UDP не используется вовсе (ни в LAN, ни на loopback);
- видеосеанс принимается только от того же пульта (URI сертификата) и с того же адреса, что текущий сеанс управления; конец или смена сеанса управления закрывает видео; GStreamer работает только пока есть сеанс;
- пульт подключается только к блоку текущего сеанса управления, порт — из своей конфигурации (не из телеметрии); незащищённого удалённого источника нет; при потере управления видео выключается;
- задержка — по встроенным PING/PONG (оценка смещения часов, как в NTP) и времени отправки каждого пакета; разрешение — по SPS потока.

Включение — полем `video` в `~/.config/sheregesh/link.json` (по умолчанию включено; persistent — переживает DEV deploy и rollback). Юниты образа не меняются: код доставляется DEV deploy.

## Ограничения

- TCP: потеря пакета в LAN задерживает поток (нет выпадения кадров); при перегрузке кадры теряет источник.
- Видео не шифруется отдельно от TLS-канала (это и есть защита); пропускная способность ограничена одним TCP-соединением.
- Автономный режим (одна плата, `sheregesh-remote-emu`) по-прежнему использует RTP/UDP только на 127.0.0.1.
- Если понадобится UDP-видео между платами (например, при радиоканале в будущих версиях), — SRTP с ключами через mTLS после добавления `python3-gi` в образ, отдельным решением.
