# ADR-0015. Кадр видео пульта мимо Python: dmabuf по unixfd → qml6glsink

- **Статус:** Предложено, 2026-10-26. Код и образ готовы; на плате не проверено — нужна пробная загрузка
  образа `db36670` на pi1 (OTA установлен в слот A, переключение слотов не выполнялось).
- **Связано:** ADR-0011 (видеоканал TLS, декодер отдельным процессом, без python3-gi в процессе пульта — здесь
  пересматривается последнее), ADR-0002/0006 (образ, A/B), `docs/acceptance/ui-minimal/REPORT.md` (матрица видео).

## 1. Контекст

Кадр сейчас идёт так: декодер gst-launch (отдельный процесс) → масштаб и `videoconvert` в RGBx → stdout → Python
читает кадр → `QPainter` рисует его в текстуру. Матрица с камерой (Pi 5 + IMX477, H.264 1280×720, 30 к/с) на GPU pi1:

| Кадр на пульте | Пульт CPU | gst CPU | к/с | Задержка в пульте p50 / p95 |
|---|---|---|---|---|
| 640×360 (сейчас, кадр по приходу) | 33 % | 28 % | 30 | 5 / 9 мс |
| 960×540 | 87 % | 68 % | 30 | 16 / 22 мс |
| 1280×720 | 65–112 % | 78–96 % | 12–23 | 29–31 / 38–46 мс |

Полное разрешение камеры Pi 4 по этому пути не держит: каждый кадр 1280×720 — 3,7 МБ через Python и конвертация
цвета на CPU. Владелец: «минимальное время отклика при максимально возможном качестве», новый образ допустим.

## 2. Решение

```
pi2 ─RTP/TLS─▶ пульт (Python: TLS и пакеты, как в ADR-0011)
                 │ stdin
     процесс gst-launch: rtpstreamdepay → rtph264depay → h264parse → v4l2h264dec → unixfdsink
                 │ дескрипторы dmabuf по unix-сокету ($XDG_RUNTIME_DIR, на поколение конвейера)
     процесс пульта: unixfdsrc → queue(1, leaky) → glupload → glcolorconvert → qml6glsink → GstGLQt6VideoItem
```

- Декодер остаётся отдельным процессом (его сбой не роняет интерфейс, перезапуск — прежний `VideoReceiver`).
- В процессе пульта — только приёмник GStreamer (GObject Introspection). Пиксели через Python не идут; Python видит
  отметку «кадр дошёл до qml6glsink» (проба) — для состояния, FPS и счётчиков; `FRAME_WAKE` прежний.
- Включается автоматически, только если есть всё: Minimal, `python3-gi` + `gstreamer1.0-gl` + `gstreamer1.0-qt6`,
  H.264 с `v4l2h264dec` и `unixfdsink`, окно на экране (без дисплея qml6glsink не получит контекст GL). Иначе — прежний
  путь RGBx, без изменений поведения. `SHEREGESH_VIDEO_GL=0` — выключить.
- Сцена Qt — OpenGL (`QQuickWindow.setGraphicsApi(OpenGL)`), общий контекст с qml6glsink.
- Сбой приёмника GL (ошибка, EOS) завершает декодер — `_poll` перезапускает конвейер, как при любом выходе декодера.
- Источник без сигнала: поверх элемента GL — чёрное поле (прежний кадр не выдаётся за текущий, как в `VideoView`).

## 3. Образ

`tools/image/build_deb.py` → зависимости пакета: `gstreamer1.0-gl`, `gstreamer1.0-qt6`, `python3-gi`,
`gir1.2-gstreamer-1.0`, `gir1.2-gst-plugins-base-1.0` (trixie 1.26.2 = GStreamer платы), `qml6-module-qtquick-shapes`.
Образ `db36670` собран на devbox (verify 0, owners = эталон, order_check PASS), OTA-пакет `ee3ec8a0…0988`
воспроизводим. Тем же образом на платы приходит UART3 (ADR-0014).

## 4. Риски и проверки на плате (до решения «Принято»)

1. qml6glsink в процессе PySide6 (не PyQt): регистрация типа QML, свойство `widget` (gpointer из адреса C++).
2. Импорт dmabuf `v4l2h264dec` → `glupload` на V3D под Wayland/cage; если не пойдёт — одно копирование в C внутри
   glupload (всё равно без Python).
3. Матрица `ui_bench.py --gl --rtsp` 30 с: CPU, к/с, задержка; 1280×720 и выше — цель 30 к/с при задержке в пульте
   не больше нынешних 640×360.
4. Без дисплея (как сейчас на pi1) — прежний путь, видео 30 к/с, OTA confirm роли console не страдает.

## 5. Отвергнуто

- Qt Multimedia (`QVideoSink`): YUV-шейдеры готовые, но кадр всё равно копируется из Python в `QVideoFrame`.
- `qml6glsink` с декодером в процессе пульта: меньше звеньев, но сбой декодера/драйвера V4L2 роняет интерфейс.
- Разделяемая память + свой шейдер YUV без новых пакетов: убирает копии частично, сложнее и всё равно через Python.
