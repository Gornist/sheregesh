# ADR-0016. Видео блок → пульт: SRTP по UDP внутри GStreamer, ключи по SHRG-LAB (mTLS)

- **Статус:** Предложено → реализовано и проверено на двух платах 2026-10-27 (уровни 0–1 PASS; три физических отключения Ethernet PASS, искусственные потери NOT TESTED —
  `docs/acceptance/adr0016/REPORT.md`); «Принято» — после завершения проверки искусственных потерь. Пересматривает ADR-0011 в части транспорта видео между платами.
  Решения владельца 2026-10-26: видео — отдельная служба со своим жизненным циклом и диагностикой, не часть GUI
  (§3.1); правило nftables «UDP видео на пульте — только с адреса блока» входит в образ (§3.3, §7.1).
- **Связано:** ADR-0011 (видеоканал TLS 1.3 + mTLS — остаётся резервным путём), ADR-0007 (SHRG-LAB, правило
  совместимости TL-004/CHG-012), ADR-0015 (кадр пульта мимо Python, python3-gi в образе), ADR-0006/0009 (образ, OTA).
- **Требования:** не меняются. Касается REQ-SW-002 (видео), REQ-SW-005 (секреты в журналах), REQ-UPD-009
  (раскрытие секретов), профиля TL-005 (взаимная аутентификация устройств).

## 1. Контекст

Сейчас (ADR-0011) каждый RTP-пакет проходит через Python на обеих платах: блок читает `rtpstreampay` из stdout
`gst-launch`, ставит метку времени и пишет в TLS; пульт читает TLS (два `recv` на пакет) и пишет в stdin декодера.
Транспорт — TCP.

Замеры 2026-10-26, pi2 → pi1, 720p30, H.264 6 Мбит/с (живой поток, по 60 с):

| Участок | p50 | Чем измерено |
|---|---|---|
| Кодер pi2 (YUYV в `v4l2h264enc` напрямую) | ≈ 10 мс | стенд на pi2 |
| Передача: метка блока → запись последнего пакета кадра в декодер пульта | 3,5–4,7 мс (p95 8–11, макс. 15–24) | `ui-state.json` пульта |
| Разбор и аппаратный декодер pi1 | ≈ 10 мс | стенд на pi1 |
| Кадр до экрана (путь GL, ADR-0015) | ≈ 5 мс | замер сессии S8 на виртуальном выходе cage |

RTT между платами — 0,7 мс, то есть из 3,5–4,7 мс передачи сама сеть занимает около миллисекунды, остальное —
Python и TLS. При переходе 2 → 6 Мбит/с передача выросла с 2,3 до 4,8 мс: втрое больше пакетов через Python.
`TCP_NODELAY` p50 не изменил (снизил максимум 24 → 18 мс), крупные RTP-пакеты (`mtu=60000`) перенесли время из
передачи в декодирование без выигрыша в сумме. Резерв этого пути — около 3 мс p50 плюс выбросы; он исчерпан без смены
архитектуры.

Есть и вторая причина. TCP задерживает весь поток при потере одного пакета. На проводе потерь нет, но для будущего
радиоканала (D6) нужен транспорт, который теряет пакет, а не останавливает видео.

Почему SRTP отклонили в ADR-0011: на платах не было python3-gi, и ключ можно было передать `srtpenc`/`srtpdec` только
через командную строку `gst-launch` (видна любому процессу через `/proc/<pid>/cmdline`). С ADR-0015 python3-gi и
привязки GStreamer входят в зависимости пакета (`tools/image/build_deb.py`); на pi1 они есть (образ `db36670`),
на pi2 — нет (образ `bd74c8c`).

Проверено на обеих платах (GStreamer 1.26.2): `srtpenc`/`srtpdec` (шифры `aes-128-icm`, `aes-256-icm`,
`aes-128-gcm`, `aes-256-gcm`), `dtlssrtpenc`, `rtpbin`, `rtphdrextntp64`, `rtprtxsend`, `rtpulpfecenc`. Межсетевого
экрана на платах нет (nftables не активен, правил в образе нет).

## 2. Варианты

**A. Оставить TLS/TCP через Python (ADR-0011).** Работает и проверен. Недостатки — Python на каждом пакете
(≈ 3 мс p50, выбросы до 15–24 мс, растёт с битрейтом) и блокировка потока TCP при потерях.

**B. SRTP по UDP, ключи — сообщением SHRG-LAB по mTLS (выбрано).** Пакеты идут только по потокам GStreamer.
Python строит конвейер через python3-gi, задаёт ключ свойством объекта (не командной строкой), читает статистику раз
в секунду, перезапускает. Аутентификация устройств — та же, что у канала управления (CA стенда, URI сертификата).
Цена — новый образ на pi2, сообщение протокола 1.5, жизненный цикл ключей.

**C. DTLS-SRTP (`dtlssrtpenc`/`dtlssrtpdec`).** Ключи не покидают GStreamer. Но элементы DTLS по умолчанию
принимают любой сертификат: проверку против CA стенда и URI пришлось бы делать по сигналам из Python — второй,
независимый от SHRG-LAB путь аутентификации. Плюс рукопожатие DTLS при каждом перезапуске конвейера. Отложено: если в
B понадобится независимость видеоканала от канала управления, — отдельным решением.

**D. Ретранслятор на C или Rust вместо Python, транспорт TLS/TCP.** Убирает Python из пути пакетов, но оставляет
блокировку TCP и требует новой цепочки сборки для плат. Выигрыш по p50 тот же порядок, что у B, без пользы для
радиоканала.

**E. kTLS.** Модуль `ssl` Python не даёт передать сеанс ядру; всё равно нужен нативный код (см. D). Отклонено.

**F. WebRTC (`webrtcbin`).** Обмен SDP, ICE, libnice — для двух узлов со статическими адресами избыточно. Отклонено.

**G. RTP по UDP без шифрования.** Нарушает профиль TL-005 (обмен между платами аутентифицирован и защищён). Отклонено.

## 3. Решение (вариант B)

```
pi2: служба sheregesh-video-tx (python3 + gi)
     источник (как сейчас) → [кодер или сквозной H.264] → rtph264pay mtu=1200 + rtphdrextntp64
       → rtpbin (RTCP) → srtpenc (ключ — свойство объекта) → udpsink → пульт:video_port
pi1: служба sheregesh-video-rx (python3 + gi)
     udpsrc (лабораторный интерфейс) → srtpdec (ключ — в caps-объекте, не строкой)
       → rtpbin/rtpjitterbuffer → rtph264depay → h264parse → v4l2h264dec → unixfdsink ─┐
GUI пульта: unixfdsrc → glupload → qml6glsink (ADR-0015) ←─────────────────────────┘ (только показ)
```

### 3.1. Видео — отдельная служба

Видео на обеих платах — самостоятельная служба systemd, а не дочерний процесс GUI или агента.

- **Жизненный цикл.** `sheregesh-video-rx.service` (pi1) и `sheregesh-video-tx.service` (pi2): `Type=notify`,
  сторож `WatchdogSec`, `Restart=on-failure`, свой предел перезапусков. Перезапуск или сбой GUI не прерывает приём
  и декодирование; сбой службы видео не трогает GUI и агент — GUI показывает «нет видео» и ждёт кадры на том же
  сокете. Конвейер внутри службы перезапускается сам (как сейчас `VideoReceiver._poll`), служба — только при
  собственном сбое или потере сторожа.
- **Кто владеет сеансом.** Сеанс SHRG-LAB по-прежнему у агента блока и у клиента канала в GUI пульта: они проверяют
  идентичность второй стороны, получают или создают ключ и передают службе команды по локальному unix-сокету
  (`$XDG_RUNTIME_DIR/sheregesh-video.sock`, права 0600, проверка `SO_PEERCRED` — только учётная запись стенда):
  `start {gen, ssrc, key, peer, port}`, `stop`, `status`. Нет действующего сеанса управления — нет команды `start`,
  служба держит конвейер остановленным и ключа не хранит.
- **Диагностика.** Служба сама публикует состояние в `$XDG_RUNTIME_DIR/sheregesh-video/state.json` раз в секунду:
  поколение, кадры принятые и декодированные, к/с, задержка «отправка → декодирован» p50/p95/макс, потери RTP,
  отброшенные SRTP (тег, повтор), PLI, перезапуски конвейера, ошибки VideoCore из `dmesg`. GUI и агент только читают
  это состояние; health-проверка OTA (ADR-0009) проверяет службу видео отдельно от GUI. Журнал — свой
  (`journalctl -u sheregesh-video-*`), без ключа (T1).
- **Ресурсы.** Свои ограничения юнита: `Nice`/`CPUSchedulingPolicy` для потоков GStreamer, `MemoryMax`, привязка
  к ядрам — подбираются замером; `LimitCORE=0`.
- **Процесс внутри службы.** Python только управляет: строит конвейер, задаёт ключ, раз в секунду читает статистику,
  обслуживает сокет команд. Пробников на каждый пакет нет; метка «кадр декодирован» — пробник на выходе декодера
  (30 раз в секунду) в процессе службы, где нет другой работы на Python и GIL свободен.
- **Режим без двух плат** (эмуляторы, x86, одна плата): та же служба или тот же модуль, запущенный лаунчером,
  с передачей через 127.0.0.1.
### 3.2. Ключи, восстановление, задержка

- **Ключ.** Блок генерирует мастер-ключ и соль (`os.urandom`, AES-128-GCM: 16 + 12 байт) на каждое поколение
  конвейера: новый видеосеанс, смена источника, любой перезапуск отправки. Новое поколение — новый случайный SSRC.
- **Передача ключа.** Новое сообщение SHRG-LAB 1.5 `video-key` блок → пульт по действующему сеансу mTLS:
  `{gen, ssrc, cipher, key}`; пульт отвечает `video-key-ack {gen}`. Блок отправляет видео поколения `gen` только после
  подтверждения. Порт приёма — из конфигурации пульта (как `video_port` сейчас), адрес — адрес текущего сеанса
  управления; из телеметрии адрес не берётся.
- **Передача ключа в службу.** Только командой `start` по локальному unix-сокету с проверкой `SO_PEERCRED`
  (§3.1). Ключа нет в `argv`, переменных окружения, файлах, журналах, состоянии и телеметрии; служба держит его
  в памяти до `stop` или конца поколения.
- **Конец сеанса.** Конец или смена сеанса управления останавливает отправку и уничтожает ключ на обеих сторонах
  (как в ADR-0011 закрывается TLS-видеосеанс). Шифр `null` запрещён в коде.
- **Восстановление.** Пульт шлёт RTCP PLI при потере опорного кадра; блок отвечает событием принудительного ключевого
  кадра в кодер (`GstForceKeyUnit`, у `v4l2h264enc` — элемент «Force Key Frame»). При сквозном H.264 с камеры
  ключевой кадр ждёт интервала камеры, это фиксируется в состоянии источника. RTX и FEC — не в первой версии.
- **Задержка.** Время отправки — в расширении заголовка RTP (`rtphdrextntp64`, RFC 6051), смещение часов — по
  существующим PING/PONG SHRG-LAB. Пульт считает «отправка блоком → кадр декодирован» в службе видеоприёма (§3.1); метрики
  в её состоянии и в `ui-state.json` те же, что сейчас, плюс потери и отброшенные SRTP-пакеты.

### 3.3. Межсетевой экран порта видео (решение владельца)

- Образ содержит таблицу nftables `inet sheregesh_video`, которая касается **только портов видео**; остальной
  трафик не фильтруется (общего межсетевого экрана в образе по-прежнему нет):
  `udp dport { video_port, video_port+1 } ip saddr != @peer drop` со счётчиком отброшенных пакетов.
- **Пульт** принимает UDP видео и RTCP только с адреса блока; **блок** — RTCP только с адреса пульта.
- Набор `@peer` по умолчанию пуст: до установления сеанса управления весь UDP на порты видео отбрасывается.
- Адрес задаётся в момент установления сеанса SHRG-LAB, а не константой образа: на стенде адреса выдаёт DHCP,
  а пульт может искать блок (`discover`). Агент блока и клиент канала GUI работают без root, поэтому набор меняет
  шаблонный юнит `sheregesh-video-allow@<IPv4>.service` (oneshot, root, `nft` — замена единственного элемента
  набора). polkit разрешает учётной записи стенда запускать только этот шаблон и только с адресом IPv4 из
  лабораторной сети (проверка шаблона экземпляра в правиле). Конец сеанса — `sheregesh-video-allow@none`.
- Счётчик отброшенных пакетов nftables — в состоянии службы видео (§3.1).

### 3.4. Прочее

- **Совместимость.** `video.transport`: `srtp` | `tls` | `auto` (по умолчанию). В `auto` — SRTP, если обе стороны
  объявили в `hello` протокол ≥ 1.5 и возможность `srtp` (есть python3-gi и элементы); иначе — TLS по ADR-0011.
  Путь TLS не удаляется, пока B не принят на обеих платах.

## 4. Угрозы

| № | Угроза | Мера | Проверка |
|---|---|---|---|
| T1 | Раскрытие ключа: командная строка, окружение, журналы, телеметрия, дамп памяти, чужой локальный процесс | ключ только в сообщении mTLS и в команде `start` по unix-сокету 0600 с проверкой `SO_PEERCRED`; поле `key` маскируется в журналах SHRG-LAB и службы видео; `LimitCORE=0` у юнита службы | канарейка `SHRG-CANARY-VIDEOKEY-…` в тестах: нет в `/proc/*/cmdline`, `/proc/*/environ`, журналах, телеметрии, экспортах (REQ-SW-005) |
| T2 | Повтор гаммы: тот же ключ и SSRC при повторе номера пакета (перезапуск конвейера, переписывание номеров `RtpContinuity`) | новый ключ и SSRC на каждое поколение; на пути SRTP номера не переписываются, пульт принимает новое поколение по `video-key` | модульный тест: никакие два поколения не получают одинаковую пару (ключ, SSRC); системный тест перезапуска источника |
| T3 | Подложные пакеты на UDP-порт пульта из LAN | тег аутентификации SRTP — пакет отбрасывается до депакетизации; счётчик отброшенных в состоянии | системный тест: изменённый байт, чужой ключ, открытый RTP → 0 кадров, счётчик растёт |
| T4 | Повтор перехваченных пакетов | окно повторов libsrtp (`srtpdec`) | системный тест: повтор записанных пакетов → отброшены |
| T5 | Перегрузка порта потоком мусора, чужие пакеты | nftables: на порты видео — только адрес второй платы текущего сеанса (§3.3), до сеанса — ничего; за ним тег SRTP | системный тест: пакеты с чужого адреса отброшены nftables (счётчик), с адреса блока чужим ключом — отброшены SRTP; CPU пульта при потоке мусора 50 Мбит/с |
| T6 | Понижение до открытого RTP | `null` запрещён; транспорт выбирает канал mTLS, без него видео нет | модульный тест конфигурации |
| T7 | Ключ живёт после конца сеанса управления; команды службе от чужого процесса | `stop` при конце сеанса, набор nftables очищается; сокет команд — только учётная запись стенда | системный тест: обрыв управления → видео остановлено ≤ 2 с, процесс без ключа |
| T8 | Метаданные (размеры и время пакетов) | принимается, как и в ADR-0011 | — |

## 6. Что меняется в образе (обе платы)

- **Пакеты.** Нужны python3-gi, `gir1.2-gstreamer-1.0`, `gir1.2-gst-plugins-base-1.0` — уже в зависимостях пакета
  (ADR-0015). pi2 сейчас на образе `bd74c8c`, где их нет; нужен образ не старше `db36670` (единый для обеих плат),
  установка через OTA (ADR-0009). `gstreamer1.0-plugins-bad` (srtp) уже есть.
- **Сеть.** Пульт открывает UDP `video_port` (по умолчанию 7444, тот же номер, что TCP сейчас) и RTCP `video_port+1`
  на лабораторном интерфейсе. Блок слушает RTCP `video_port+1`.
- **Межсетевой экран (§3.3).** Пакет `nftables`, таблица `inet sheregesh_video` (только порты видео, набор `@peer`
  пуст при загрузке), юнит-шаблон `sheregesh-video-allow@.service`, правило polkit для него. Проверка в
  `tools/image/verify_image.py`: таблица загружается при старте, набор пуст, правило polkit ограничено шаблоном.
- **Службы (§3.1).** Новые юниты `sheregesh-video-rx.service` (роль console) и `sheregesh-video-tx.service` (роль
  remote) с `Type=notify`, сторожем, `LimitCORE=0`; запуск — по роли платы. Новые юниты требуют нового образа;
  код самих служб дальше доставляется DEV deploy (если служба запускается через launcher, как приложения сейчас).
  Правило polkit — перезапуск этих служб учётной записью стенда, как для существующих.
- **Конфигурация.** Поле `video.transport` в `~/.config/sheregesh/link.json` (по умолчанию `auto`).

## 8. План проверки

**Без плат (CI, x86, эмуляторы).**
1. Модульные: генерация ключа и SSRC на поколение; схема `video-key`/`video-key-ack`; маскирование поля `key` в журнале;
   выбор транспорта в `auto` (1.4 или нет python3-gi → TLS); запрет `null`.
2. Службы: сбой и перезапуск GUI не прерывают приём (кадры в службе продолжаются, GUI снова показывает видео ≤ 1 с
   после старта); сбой конвейера — перезапуск внутри службы ≤ 1 с; зависание службы — сторож systemd; команды
   по сокету от чужой учётной записи отклоняются; состояние службы публикуется раз в секунду.
   Системные: две службы, SRTP через 127.0.0.1; изменённый байт, чужой ключ, открытый RTP, повтор пакетов → 0 кадров и
   счётчик; перезапуск источника → новое поколение, видео восстановилось ≤ 1 с; обрыв управления → видео остановлено
   ≤ 2 с; канарейка ключа не найдена в `/proc/*/cmdline`, `/proc/*/environ`, журналах, телеметрии, экспортах.

**На платах** (после OTA обеих плат на образ со службами видео, nftables и python3-gi; проверка nftables:
пакеты на порт видео с третьего адреса стенда отброшены и посчитаны, до сеанса управления отброшено всё; каждый прогон — с таймаутом и проверкой vchiq и рабочего потока).
3. Задержка «отправка → декодирован», 720p30 6 Мбит/с, 3 × 60 с: SRTP против TLS. Цель — p50 ниже на ≥ 2 мс,
   p95 и максимум не выше, CPU обеих плат не выше.
4. Джиттер-буфер 0 / 10 / 20 / 50 мс: p50, p95 и доля выпавших кадров без потерь в сети.
5. Потери 0,5 / 2 / 5 % (способ — решение владельца §7.2): время восстановления картинки после PLI, доля кадров
   с артефактами; поток не останавливается целиком.
6. Длительная работа 3 ч: нет роста p95 (R5), нет утечек памяти, нет ошибок VideoCore.
7. С физическим дисплеем на pi1: путь GL и полная задержка «от стекла до стекла» по каждому устройству захвата (R2, R3).

захвата; канарейка ключа нигде не найдена.
