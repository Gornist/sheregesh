# ADR-0018. Сервис сборки образов на devbox: очередь, гейты до железа, раскатка только проверенного

- **Статус:** Принято владельцем 2026-10-30 («да, делай, постарайся ускорить сборку»); реализация — `tools/build/`.
- **Повод:** решение владельца 2026-10-30 после сессии, в которой образ, не проверенный на настоящей загрузке,
  дважды ушёл на карты, сборка на Mac заполнила диск до нуля, а две сборки на devbox молча оборвались на 25-й минуте.
- **Связано:** ADR-0002 (сборка образа), ADR-0006/0009/0010 (A/B, OTA, DEV deploy), `docs/development/STAND-WORKFLOW.md`
  (аренды плат). Требования не меняются.

Общий вывод: почти каждый дефект, дошедший до железа, проявлялся **только при загрузке** (п. 3, 4, 11–13) или
был пойман гейтом, который запускали вручную и не всегда (п. 1, 2). Остальное — среда сборки и ручной поток.

## 2. Практики (источники в конце)

- **Загрузочный тест образа до железа.** systemd проверяет свои образы mkosi загрузкой под `systemd-nspawn` и под
  QEMU, с тайм-аутом, аварийная оболочка заменена выключением, журнал сохраняется при сбое. Признак успеха —
  явный (код выхода, маркер), признаки провала ищутся в журнале.
- **nspawn** загружает полный корень (`--boot`), умеет `--read-only` и `--network-veth`; это средство испытаний,
  не граница безопасности.
- **QEMU `raspi4b`** грузит ядро Pi 4 с dtb, но в тестах QEMU — с внешним ядром и initrd, полной загрузки образа
  Raspberry Pi OS нет; прошивку, tryboot и VideoCore не эмулирует. Для нас — второй уровень, не замена железа.
- **A/B (RAUC/Mender/SWUpdate):** откат — свойство загрузчика; новый слот «на испытании» до явного mark-good
  после ограниченного по времени детерминированного health check; флаки-проверки — главная причина лишних
  откатов. Mark-good — только если нет упавших юнитов (`is-system-running` внутри юнита ненадёжен).
- **Воспроизводимость:** `SOURCE_DATE_EPOCH` от времени коммита; две сборки и сравнение (OpenWrt, Buildroot —
  diffoscope). У нас уже `cmp` пакета OTA двух сборок.
- **rpi-image-gen** нацелен на воспроизводимые артефакты, лучше всего работает на arm64-хосте; в CI — только при
  детерминированных сценариях.
- **Аппаратный контур (labgrid, LAVA):** управление питанием и SD-мультиплексором, pytest поверх; следующий шаг
  после контейнерных гейтов, если понадобится автоматическая проверка на платах без рук.

## 3. Решение

### 3.1 Где и кем

Сервис **`shbuild`** на devbox: CLI + одна служба-исполнитель (systemd user/system unit). Mac только отправляет
задание по SSH и забирает артефакты, когда нужно писать карту. **На Mac — никаких сборок, Docker и контейнерных
проверок.** Свои инструменты (Woodpecker, Forgejo Actions, self-hosted раннер GitHub) отклонены: один
пользователь и один исполнитель, работа с непушнутыми коммитами, публичный репозиторий (раннер на devbox для
публичного репозитория — риск от чужих PR). Формат отчётов совместим с будущим CI.

### 3.2 Задание и конвейер

`shbuild submit <коммит>` — коммит приходит git bundle (как сейчас, но автоматически) или из `origin`. Дерево
сборки — `git worktree` этого коммита (не rsync), `SOURCE_DATE_EPOCH` — время коммита, ключи и переменные —
из конфигурации сервиса. Одно задание за раз; остальные в очереди.

| Этап | Что | Время | Сбой останавливает |
|---|---|---|---|
| 0 preflight | свободно на диске ≥ 40 ГБ, память ≥ 6 ГБ, `binfmt` qemu-aarch64 зарегистрирован, Docker жив, нет чужой сборки | с | да |
| 1 быстрые проверки | `pytest tests/tools tests/unit` (в контейнере CI); проверка хуков слоёв: каждый хук `customize` прогоняется на пустом корне-каталоге с заглушками (ловит п. 14) | 1–3 мин | да |
| 2 сборка | `os/docker-build.sh` в cgroup `MemoryMax`, `TimeoutSec`; журнал этапов | ~35 мин | да |
| 3 статические гейты | verify_image, owners_check против эталона, order_check ×8, SHA256SUMS, `dirty: false` | 3 мин | да |
| 4 загрузочный тест | весь диск образа в **QEMU virt** (aarch64, TCG) с ядром Debian; сценарии **console**, **remote**, **свежая плата без роли** (п. 13); проверки: нет упавших юнитов, имя после DHCP и продления, источник времени, sshd и root по ключу, `/var` засеян | ~4 мин × 3 | да |
| 6 итог | `report.json` (все этапы, коды, версии), статус **CANDIDATE** или **FAILED@этап** | — | — |

Конечные состояния всегда явные: `PASSED`, `FAILED@<этап>`, `ERROR@<этап>` (сбой среды), `CANCELLED`, `TIMEOUT`.
`shbuild wait <id>` печатает ровно одну строку конечного состояния — по ней смотрит агент (п. 15).

Почему QEMU, а не контейнер (проверено на devbox 2026-10-30): devbox — x86, контейнер с корнем arm64 работает через
qemu-user, а тот не поддерживает сетевые пространства имён и песочницу юнитов — journald, resolved и юниты с
`PrivateNetwork` падают ложно. В QEMU virt ядро настоящее; на старом образе bc87d16 тест воспроизвёл ровно дефект
плат (упавший `sheregesh-hostname`, имя `sheregesh-dev` после DHCP). Отличия от платы: ядро Debian, нет прошивки,
tryboot, VideoCore, дисплея, GPIO/UART, Bluetooth.

**Пакет OTA** подписывается ключом владельца, который не покидает Mac, поэтому сборка пакета ×2 + `cmp` и L3-установка
остаются шагом раскатки на Mac (`shdeploy ota-build`, `tools/deploy/ota-check`), из артефактов кандидата PASSED.

**Ускорение:** готовый контейнер-сборщик (`tools/build/make_builder.sh`, один раз на ревизию rpi-image-gen) — без
установки пакетов под эмуляцией в каждой сборке; время каждого этапа — в журнале и отчёте. Следующий кандидат —
сборка с инструментами x86 и эмуляцией только chroot (rpi-image-gen это умеет); включается только после того, как
такой образ пройдёт все гейты и совпадёт по содержимому с эмулированной сборкой.

### 3.3 Хранение и место

Артефакты — `~/shbuild/artifacts/<коммит>/`; хранятся: все развёрнутые на платах (по `ota-status`), последние 5
кандидатов, всё с пометкой `keep`. Рабочий том сборки и `src-*` чистятся после задания. Проверка места — до
старта и перед каждым этапом. На Mac — только образ для записи карты, удаляется после записи.

### 3.4 Раскатка на железо

Раскатка остаётся отдельным шагом (`shdeploy`), только по явному «да» владельца, и **принимает только кандидата
с `report.json` PASSED** того же SHA образа. Порядок: аренда плат (`stand_lease`), pi1 первым, tryboot с одним
повтором при игнорировании прошивкой (п. 10), после загрузки — автоматические проверки (`check_link`,
`check_video_link`, имя, время, health) и только потом confirm; провал — без confirm, плата сама возвращается.

### 3.5 Доступ на платах

DEV-образ: root по SSH только по ключу (решение владельца 2026-10-30), пароли выключены. Строгий образ без
изменений.

## 4. Последствия

- Сборка дольше на ~15 минут (тесты, загрузка, двойной пакет), зато дефекты 3, 4, 11–14 ловятся до карт и OTA.
- Загрузочный тест не проверяет прошивку, tryboot, VideoCore, дисплей, GPIO/UART: они остаются за платами.
- Следующий шаг, если понадобится: автоматический аппаратный контур (реле питания, SD-mux, labgrid).

## 5. План внедрения (после согласования)

1. `tools/build/shbuild/` — CLI, очередь (каталоги заданий, файл блокировки), исполнитель, `report.json`; тесты.
2. Этап 4 из `tools/image/boot_check.sh` (ветка `fix/hostname-ota`), расширенный сценариями ролей.
3. Проверка хуков слоёв (этап 1).
4. Установка службы на devbox, перенос ключей и эталона owners в конфигурацию.
5. `shdeploy`: отказ без отчёта PASSED.
6. Первый прогон — коммит с исправлением имени и root; на платы — OTA только после PASSED.
