# ADR-0019. Сборочный хост shbuild на Raspberry Pi 5 с NVMe

- **Статус:** Принято владельцем (запрос 2026-11-02: «использовать этот rpi5 как конвейер по сбору arm образов»; план —
  2026-10-30, `docs/development/ROADMAP.md`). **Работает с 2026-11-02**; devbox остаётся хостом по умолчанию до
  отдельного решения о переключении. Реализация — `os/`, `tools/build/`.
- **Связано:** ADR-0018 (сервис сборки), ADR-0002 (образ), `docs/development/BUILD-SERVICE.md` (устройство),
  `docs/development/BUILDHOST-PI5.md` (порядок действий с платой).

## Решение

1. **Образ хоста — отдельная конфигурация** `os/config/sheregesh-buildhost-pi5.yaml` + слой
   `os/layer/sheregesh-buildhost.yaml`. Это не продуктовый образ: ни пульта, ни A/B, ни OTA, ни пакета sheregesh.
   Разметка Raspberry Pi OS (MBR: `BOOT` vfat 512 МиБ + `ROOT` ext4 6 ГиБ), корень при первой загрузке растёт до
   конца носителя (`shbuild-growroot`). ext4 с блоком 4 КиБ, а не 16 КиБ (размер страницы ядра Pi 5): такой корень
   монтируется и ядром Pi 5, и ядром Debian загрузочного теста.
2. **Состав:** Docker (`docker.io`, `docker-cli`), git, rsync, zstd, python3, `iproute2`, `nvme-cli`, `smartmontools`,
   `rpi-eeprom` (обновление EEPROM замаскировано — только явной процедурой), аппаратный сторож systemd, журнал на
   диске, mDNS (`pi5.local`). Вход — только по ключу (root тоже, как у DEV-образов, решение 2026-10-30); пользователь
   `shbuild` в `docker` и `sudo`. PCIe x1 для NVMe включён в `config.txt` (`dtparam=pciex1`, Gen 2: для сборочной
   машины устойчивость важнее скорости).
3. **Память.** У платы 2 ГБ ОЗУ. Хост держит zram и **файл подкачки 8 ГиБ на NVMe** (`shbuild-swap`, создаётся после
   расширения корня; при диске < 16 ГиБ свободного места пропускается без ошибки). `preflight` shbuild считает
   «ОЗУ + свободная подкачка на диске ≥ 6 ГБ при ОЗУ ≥ 1 ГБ» (zram не в счёт). Сборка продуктового образа использовала
   подкачку на 0 МБ.
4. **Собирается только через shbuild** (правило ADR-0018 не меняется): `submit --config sheregesh-buildhost-pi5`.
   Задание получает свой каталог артефактов (`<коммит>.<конфигурация>`), проверку структуры
   (`tools/image/verify_buildhost.py`) и загрузочный сценарий `buildhost`. Гейты owners-эталона и порядка юнитов
   относятся к A/B-образу «Шерегеша» и к хосту не применяются; SBOM образа обязателен.
5. **Сервис переносится, а не дублируется:** на arm64-хосте `preflight` не требует `binfmt qemu-aarch64`, загрузочный
   тест идёт на KVM (`/dev/kvm`); остальной код сервиса тот же. Установка — `SHBUILD_HOST=shbuild@pi5.local
   SHBUILD_BULK_HOST=shbuild@pi5.local python3 tools/build/shbuild.py install`.

## Результат (2026-11-02)

Продуктовый образ `sheregesh-lab-dev-pi4` на Pi 5, `PASSED`: **≈ 10 мин** против ≈ 37 мин на devbox (`build` ≈ 7,5 против
31,5 мин; `boot` ≈ 2,5 мин на KVM против 5–7 мин в эмуляции). Путь от 25 до 10 минут — ускорения конвейера с выключателями
и откатом, перечень, замеры и отвергнутые попытки — `BUILD-SERVICE.md`, разделы 6–8.

## Не проверено (остаётся за платой)

Прошивка EEPROM и порядок загрузки NVMe при штатной эксплуатации; PCIe Gen 3; температура и устойчивость под длинной
нагрузкой; износ NVMe (на момент установки 5%, диск бывший в употреблении); работа в роли хоста при перезагрузке во
время задания (задание оборвётся, `ERROR`, очередь продолжит после старта исполнителя вручную).
