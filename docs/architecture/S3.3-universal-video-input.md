# S3.3 — Universal Video Input (универсальный видеовход)

Лабораторный стенд «Шерегеш» 1.0: пульт pi1 и удалённый блок pi2 (Raspberry Pi 4B). Задача — компактная подсистема
получения изображения с одним программным интерфейсом для синтетического генератора и обычных лабораторных устройств
захвата (USB-камера UVC, HDMI→USB-адаптер класса UVC с независимым тестовым HDMI-генератором). Подключение действующих
FPV-приёмников, проприетарные протоколы DJI, управление аппаратами и радиоканалами — вне задачи; цифровые видеоустройства
FPV рассмотрены только на уровне документированных интерфейсов вывода изображения (§2).

Статус: реализовано и проверено автоматически (L2/L3) и на настоящем GStreamer (Linux x86_64, контейнер Debian trixie).
С настоящим устройством UVC и на Pi 4 **не проверено** — оборудования нет (см. [REPORT.md](../acceptance/s3.3-video-input/REPORT.md)).
Требования не изменены; предложение изменения — §10. Гейт REQ-REL-001 — NO-GO.

## 1. Решение кратко

- **Один интерфейс `VideoSource`** (`software/sheregesh/videoinput.py`) и две реализации: `SyntheticSource` (прежний
  `videotestsrc`) и `UVCSource` (любое устройство драйвера `uvcvideo` с форматом YUYV, MJPEG или H.264). HDMI-генератор
  через HDMI→USB-адаптер — обычный `UVCSource`. Классов под изготовителей нет.
- **Конвейеры GStreamer собирает только `software/sheregesh/video.py`**, как и раньше: источник даёт голову конвейера
  (`capture()`) и декодирование своего формата (`decode()`); дальше — те же `_to_rgbx` (сначала `videoscale`, потом
  `videoconvert`), кодеры, `rtpstreampay` и т. д. Новый вход локального захвата — `capture_args(src, w, h)`.
- **Выполнение, состояние, ошибки и статистику кадров ведёт существующий `VideoReceiver`** пульта
  (`sheregesh_console/video.py`): тот же процесс `gst-launch-1.0`, тот же фоновый разбор RGBx, тот же перезапуск с
  задержкой, те же `metrics()`. Добавлен один метод `configure_local(key, opener)` и два состояния: `no-device`,
  `unsupported`. Демона нет.
- **Обнаружение — только sysfs `/sys/class/video4linux` и ioctl V4L2 из стандартной библиотеки Python**
  (`VIDIOC_QUERYCAP`, `VIDIOC_ENUM_FMT`, `VIDIOC_ENUM_FRAMESIZES`, `VIDIOC_ENUM_FRAMEINTERVALS`). Без `v4l2-ctl`
  (в образе его нет), udev-правил и новых пакетов. Устройство опрашивается и захватывается **только при явном выборе**
  источника `uvc` в конфигурации.
- **Без лишнего перекодирования**: локальный вход — только декодирование формата устройства (YUYV — никакого, MJPEG —
  `jpegdec`, H.264 — `h264parse` и декодер, выбранный пробой кодеков: `v4l2h264dec` на Pi 4). На удалённом блоке формат
  устройства, совпадающий с кодеком канала (MJPEG→jpeg, H.264→h264), передаётся **сквозным** без декодирования.
- **Защищённый видеоканал не менялся**: `videolink.py` (ADR-0011) не тронут; `VideoServer` получает готовую команду
  генератора через уже существующий параметр `command`.
- **Новых зависимостей нет.** `v4l2src`, `jpegdec`, `jpegenc`, `rtpjpegpay` — `gstreamer1.0-plugins-good`; `h264parse` —
  `gstreamer1.0-plugins-bad`; оба пакета уже в `DEPENDS` образа.

## 3. Сравнение подходов

| Подход | За | Против | Итог |
|---|---|---|---|
| **A. `gst-launch-1.0` + `v4l2src`, обнаружение sysfs/ioctl в stdlib** | всё уже в образе и в коде (`spawn` с PDEATHSIG, `_to_rgbx`, приёмник, рестарт); один процесс на поток; аппаратный H.264 Pi 4 через тот же выбор кодеков | форматы устройства надо узнать до запуска (решено ioctl) | **выбран** |
| B. µStreamer / mjpg-streamer как демон | быстрый MJPEG на Pi | новый демон, HTTP, второй конвейер, свои рестарты и права | отклонён |
| C. Python-библиотека V4L2 (linuxpy) + свой захват | без GStreamer в захвате | новая зависимость; декодирование/масштаб всё равно нужны; кадры в Python медленнее | отклонён |
| D. PyGObject (`gi`) и `GstDeviceMonitor` | обнаружение и caps силами GStreamer (так делает YStreamer) | `python3-gi` нет в образе (факт S3.1-VIDEO); встраивание GStreamer в процесс GUI | отклонён |
| E. YStreamer как готовый продукт | готовые UI, записи, DJI | отдельный образ/служба, Rust/Node, веб-интерфейс, проприетарные протоколы | отклонён (только идеи §2.1) |

### 4.1 `VideoSource` — где каждое свойство из задания

| Свойство | Где |
|---|---|
| идентификатор | `VideoSource.id`: `synthetic` или `uvc:vvvv:pppp[:serial]` (постоянный, не номер `/dev/videoN`) |
| тип интерфейса | `VideoSource.kind`: `synthetic` / `uvc` |
| доступность | `VideoSource.available`; `Unavailable(missing=…)` с причиной |
| поддерживаемые форматы | `VideoSource.formats` — все режимы устройства (`Mode`: FourCC, ширина, высота, к/с) из ioctl |
| текущее разрешение, FPS, формат | `VideoSource.mode`; `info()` → `format`, `resolution`, `fps` |
| состояние | `VideoReceiver.state`: `off | waiting | playing | no-video | restarting | unavailable | no-device | unsupported` |
| ошибки | `VideoSource.error` (обнаружение/режим) и `VideoReceiver.error` (процесс захвата) |
| статистика кадров | `VideoReceiver.metrics()`: `frames_decoded`, `decoded_fps_5s`, `restarts`, `mode: local-input`, `source` |

Состояние и статистика сознательно не дублируются в источнике: процессом управляет один общий приёмник, и для
синтетического, удалённого и UVC-режимов они считаются одинаково.

### 4.2 Обнаружение (`videoinput.scan`)

1. Перечень `/sys/class/video4linux/videoN` (без постоянного `/dev/video0`).
2. Драйвер — по ссылке `device/driver`. Всё, что не `uvcvideo` (`bcm2835-codec` `/dev/video10–12`, `bcm2835-isp`,
   `unicam`, `rpivid`), — служебный узел, **не открывается**.
3. Для `uvcvideo`: идентификатор `vvvv:pppp[:serial]` из `idVendor/idProduct/serial` USB-устройства; узел открывается
   `O_RDWR|O_NONBLOCK` только для `VIDIOC_QUERYCAP`: без `V4L2_CAP_VIDEO_CAPTURE` в `device_caps` (метаданные UVC —
   `V4L2_CAP_META_CAPTURE`) узел отбрасывается. Затем перечисление форматов, размеров и интервалов (дискретных,
   ступенчатых и непрерывных; для диапазонов проверяются только стандартные 640×480/1280×720/1920×1080 и 30/60 к/с).
4. Путь устройства для `v4l2src` — постоянная ссылка udev `/dev/v4l/by-id/…`, если есть, иначе `/dev/videoN`.
5. Ошибки (нет `/sys`, нет прав, устройство исчезло во время опроса — `ENODEV`) не исключения, а причины в `Node.reason`.

Выбор режима (`select_mode`): **точное** совпадение размера и частоты; `auto` — порядок YUYV (без декодирования) →
MJPEG → H.264. Неподходящий режим не подменяется молча — состояние `unsupported` с перечнем того, что устройство даёт.
Несколько устройств без `video_device` — ошибка с перечнем (устройство само не выбирается).

### 4.3 Жизненный цикл на пульте

- `configure_local(key, opener)`: `opener()` вызывается **при каждом запуске и перезапуске** — переподключённое
  устройство находится заново (номер узла может измениться).
- Нет устройства → `no-device`; режим не поддерживается → `unsupported`; повторный поиск раз в 2 с, процессов нет.
- Процесс захвата завершился (так `v4l2src` реагирует на отключение USB) → `restarting`, задержки 1/2/4 с, затем новый
  поиск. Кадров нет дольше 5 с при живом процессе (зависшее устройство) → процесс убивается (`killpg`) и перезапускается.
- Выключение/смена источника → `stop()`: `killpg(SIGKILL)` группы процесса, `wait()`; плюс PDEATHSIG от `spawn`.
- Событие `VIDEO-LOST` для режима `uvc` — при `no-video/restarting/no-device/unsupported`; текст события теперь
  «Нет видеопотока» (без «синтетического»).

### 4.4 Конфигурация и UI

Необязательные поля `system.yaml` (схема `console-1`, версия схемы **та же — 1**): `video_source`
(`synthetic`|`uvc`|`disabled`, по умолчанию `synthetic`), `video_device` (`vvvv:pppp[:serial]`, `videoN` или пусто),
`video_mode` (6 режимов задания), `video_format` (`auto`|`yuyv`|`mjpeg`|`h264`). Ревизии без этих полей корректны и
работают как раньше. Значение «выключено» — `disabled`, не `off`: YAML 1.1 читает `off` как `false` (найдено тестом).
Служба для проверки при изменении — `ui` (как у `system.yaml`). Хранилище — `--data-dir /var/lib/sheregesh`
(юнит `sheregesh-console`), каталог сохраняется DEV deploy и обновлением; ревизии привязаны к слоту A/B
(`ConfigStore(slot=…)`), поэтому откат на старый слот берёт свою ревизию без новых полей.

UI: на странице «Настройки» — «Видеоисточник» (Синтетический / Стандартное UVC-устройство / Выключено) и «Режим UVC».
`video_device`/`video_format` — только в YAML (резервная копия/восстановление). Страница «Видео» показывает имя
устройства, формат, разрешение, частоту режима, показанную частоту, кадры, перезапуски, состояние и причину ошибки;
внешний вид прежний, отдельных страниц нет.

### 4.5 Удалённый блок

`sheregesh_remote --video-source uvc [--video-device …] [--video-format …]` (размер и частота — существующие
`--video-width/height/fps`). Устройство находится при запуске; `/dev/v4l/by-id` переживает переподключение, каждый
видеосеанс запускает генератор заново. Без устройства блок работает, видео не объявляет и печатает
`VIDEO unavailable: <причина>`. **Юниты образа не менялись**: включение на pi2 требует решения основной сессии
(drop-in к `sheregesh-remote-net.service`), см. §9.

## 8. Ограничения

- Только устройства, которые ядро обслуживает `uvcvideo` и которые отдают YUYV/MJPEG/H.264. NV12, UYVY, GREY и пр.
  показываются в перечне, но не выбираются (нет смысла без устройства — не добавлено). Устройства с собственным
  протоколом (DJI USB, AOA) не поддерживаются.
- Режим — только точное совпадение одного из 6 режимов задания; устройства с иными размерами (например, 1024×768)
  выбрать нельзя.
- Выбор конкретного устройства при нескольких — только через `video_device` в YAML.
- Удалённый блок находит устройство один раз при запуске службы; включение — только через аргументы (юнит не менялся).
- Сквозная MJPEG через `rtpjpegpay` (RFC 2435): только JPEG 4:2:0/4:2:2 baseline; 4:4:4 элемент молча отбрасывает
  (проверено на GStreamer 1.28). Камеры UVC обычно дают 4:2:2/4:2:0; иначе — `--video-codec h264` (перекодирование).
- Тексты причин ошибок — английские диагностические строки (как прежние `decoder exited…`), в журнале и на экране.
- Задержка «стекло-стекло» (устройство, USB, дисплей) инструментом не измеряется — нужна процедура с камерой.

| Риск | Последствие | Мера |

## 11. Обоснование

Задача — один интерфейс и минимум нового. Всё, что требует поддержки (процесс GStreamer, его смерть с родителем, разбор
кадров, рестарты, метрики, защищённый канал), уже было и испытано в S2/S3.1; новое — описание источника (~360 строк,
половина — ioctl и диагностика) и один метод приёмника. Форматы определяются по ядру, а не угадываются; устройство не
трогается без явного выбора; служебные узлы Pi отсеиваются до открытия. Альтернативы (демон, внешняя библиотека,
`gi`, готовый продукт) добавляли бы процессы, пакеты или второй конвейер без выигрыша для лабораторного стенда.

## 12. Видеоприём удалённого блока (спринт 2026-10-25, ветка `video/ingest`)

Расширение S3.3 без новой подсистемы: тот же `VideoSource`, тот же `video.py`, тот же защищённый канал.

- **Источники** (`videoinput.py`): `SyntheticSource`; `V4L2Source` — любой драйвер захвата (uvcvideo, usbtv, stk1160,
  em28xx…; служебные узлы Pi не открываются), выбор по постоянному идентификатору (`/dev/v4l/by-id/*`, `by-path/*`,
  `vvvv:pppp[:serial]`, `card`, `bus_info`; `videoN` — крайний случай); аналоговые входы — `VIDIOC_ENUMSTD/G_STD/QUERYSTD`,
  PAL 720×576@25 и NTSC 720×480@30000/1001 (`v4l2src norm=`), формат UYVY; HDMI-захваты — фактические режимы
  `ENUM_FMT/FRAMESIZES/FRAMEINTERVALS`, `mode: auto`; `UVCSource` — прежний (kind `uvc`, пульт); `RTSPSource` —
  `rtspsrc protocols=tcp`, H.264/MJPEG без перекодирования, учётные данные не попадают в id/телеметрию/журнал.
- **Выполнение** (`videoingest.py`, `Ingest`): один активный источник; состояния `no-device|connect-error|starting|
  streaming|no-signal|error` (внутреннее `idle` — без видеосеанса — пульту сообщается как `starting`); «нет устройства» (узла нет, ENODEV; у RTSP — `connect-error`: сервер не принимает TCP) отличается от «нет сигнала»
  (кадров нет; или драйвер сообщает `V4L2_IN_ST_NO_SIGNAL/NO_POWER/NO_H_LOCK/NO_SYNC` через `VIDIOC_ENUMINPUT`);
  повторный поиск устройства после отключения; перезапуск зависшего конвейера с нарастающей задержкой; при перезапуске
  внутри видеосеанса номера/метки RTP продолжаются (буфер джиттера пульта не сбрасывается). `VideoServer` берёт RTP
  у `Ingest`; видеосеанс не рвётся при отключении устройства — пульт видит «нет видео» (NO_VIDEO_AFTER_S = 1,5 с,
  изображение гасится, последний кадр не показывается).
- **Конфигурация блока**: `video-input.json` рядом с `link.json` (`/home/sheregesh-ui/.config/sheregesh/`, юнит в `/usr`
  не меняется), перечитывается по `SIGHUP`: `systemctl kill --kill-whom=main -s HUP sheregesh-remote-net` (без
  `--kill-whom=main` сигнал получает вся cgroup службы; с S4 конвейеры `gst-launch-1.0` запускаются с игнорированием
  SIGHUP — `video.NO_HUP`, — поэтому и такой вызов видео не рвёт). Удалённый файл при перечитывании означает
  синтетический источник; с S4 выбор с пульта записывается в этот же файл атомарно (§13); либо аргументы
  `--video-source synthetic|uvc|v4l2|rtsp --video-device --video-mode --video-format --video-standard --video-url
  --video-rtsp-codec`. Примеры: `{"source": "v4l2", "device": "1b71:3002", "standard": "pal"}`,
  `{"source": "v4l2", "device": "534d:2109", "mode": "1280x720@30", "format": "mjpeg"}`,
  `{"source": "rtsp", "url": "rtsp://192.168.77.50:554/stream1", "codec": "h264"}`.
- **Телеметрия**: необязательный объект `status.video.source` (протокол 1.1 без изменений; старый пульт поле отбрасывает,
  новый проверяет поля и типы в `link/client.py::_sanitize_video_source`). Поля пульта (`videosource.py::remote_fields`):
  `input` synthetic|hdmi|cvbs|usb|v4l2|rtsp, `state`, `device` (без учётных данных), `error`, `width`, `height`, `fps`
  (номинальные режима; у RTSP — из потока); дополнительно `fps_actual`, `stream_width/height`, `type`, `name`, `id`,
  `format`, `standard`, `restarts`, `since_s`. INFO видеосеанса: прежние поля + `"source"` {input, type, device, width, height, fps}.
- **Ограничение**: захваты, которые без сигнала шлют «синее поле» и не сообщают статус входа (часть HDMI→UVC MS2109/
  MS2130 и EasyCAP), выглядят как `streaming` — детектора пустого кадра нет; проверяется на стенде.

## 13. Список источников и выбор с пульта (S4, ветка `s4/pipeline`)

Один активный поток, как прежде: выбор меняет описание источника и вызывает `Ingest.switch()` (старый конвейер
останавливается до запуска нового); второй конвейер не появляется.

**Контракт телеметрии** (`status.video`, необязательные поля; старый пульт их отбрасывает, новый проверяет в
`link/client.py::_sanitize_video_sources` / `_sanitize_video_select`):

- `sources` — не более 16 объектов `{id, input, name, available, active}`, порядок: synthetic, устройства V4L2, RTSP.
  `id`: `"synthetic"`; `"v4l2:<id>"` — `videoinput.stable_id`: `VID:PID[:serial]`, иначе имя ссылки
  `/dev/v4l/by-path/*` (одинаковые адаптеры без серийного номера — всегда по порту by-path), иначе `videoN`;
  `"rtsp:<n>"` — n-й элемент `rtsp_urls` (номера не сдвигаются при неверных элементах; адрес текущего `url`, которого нет в
  списке, — следующим номером). Символы id — `[A-Za-z0-9._:@+/-]`, не длиннее 96. `input` — synthetic|hdmi|cvbs|usb|
  v4l2|rtsp. `name` ≤ 64 — без учётных данных и строки запроса (`RTSP host:port/path` или метка `name` из
  конфигурации). `available` — V4L2: узел есть в sysfs; RTSP: сервер принимает TCP (без сеанса RTSP). `active` —
  источник текущего описания; выбранное, но отсутствующее устройство V4L2 остаётся в списке с `available: false`.
  Обнаружение — `videoinput.scan(probe=False)` (sysfs и ссылки udev, узлы не открываются), проверки RTSP — в фоновом
  потоке, не чаще раза в 2 с; при старте блока синхронных проб нет. `active` пересчитывается в каждом `status`.
- `select` — результат последнего `video-select` текущего сеанса управления: `{req, id, result, error}`,
  `result` — `ok` | `unknown-id` | `error` (видео выключено). `ok` с непустым `error` — переключено, но выбор не
  сохранён (нет файла конфигурации, файл нечитаем, ошибка записи) или задан `--video-source` (он важнее файла при старте).
  Новый сеанс управления сбрасывает `select`.

**Сообщение** пульт → блок, протокол **1.2** (`link/codec.py`: `TYPES["1.2"] = TYPES["1.1"] | {"video-select"}`,
`PROTOCOL_VERSION = "1.2"`): `{"type": "video-select", "body": {"id": "<id из sources>", "req": <int>}}`. Других
команд нет; блок исполняет его только в сессии 1.2 и только для id из своего списка (неизвестный id — `unknown-id`,
источник и файл не меняются). Совместимость (CHG-012): старый блок 1.1 + новый пульт → сессия 1.1, пульт не
отправляет (`video_select.state = "unsupported"`); старый пульт 1.1 + новый блок → сессия 1.1, блок такое сообщение не
исполняет (учитывает как неизвестное). ADR-0007 стоит дополнить строкой о 1.2 (не сделано в этой ветке — вне зоны).

**API пульта** (`PeerClient`): `select_video_source(source_id: str, wait_s=3.0)` — сообщение отправляет поток канала,
вызов ждёт ответ блока (`status.video.select` с тем же `req`) не дольше `wait_s`; вызывать не из GUI-потока.
Возврат `None` — принято (блок ответил `ok` или ответа ещё нет); отказ — `{"ok": false, "error": код, "detail": …}`,
коды `not-connected`, `unsupported` (сессия 1.1), `unknown` (блок не знает id), `unavailable` (видео на блоке
выключено); неверная строка id — `ValueError`. Состояние запроса — `snapshot()["video_select"] = {req, id, state}`
(`queued` → `sent`; `offline`, `unsupported`). Переключение завершено, когда у выбранного `sources[].active == true`.
Санитайзер `source` принимает и резервные состояния `reconnecting`/`retrying` (блок их пока не сообщает).

**Командная строка (стенд, приёмка)** — тот же путь, что GUI (PeerClient → `video-select`), на пульте от
`sheregesh-ui`: `python3 -m sheregesh.link.videoselect --list` и `python3 -m sheregesh.link.videoselect rtsp:0
[--wait 15]`; вывод JSON `{result, detail, active, source, sources}`, код 0 — выбран и `active`, 1 — отказ/не стал
`active`, 2 — нет связи. Блок держит один сеанс управления: команда на 1–3 с заменяет сеанс GUI, GUI переподключается сам.

**Блок**: `id` проверяется по свежему списку (sysfs без открытия узлов); выбор применяется (`Ingest.switch`; локальный
профиль UDP — перезапуск отправителя) и сохраняется в `video-input.json` атомарно (временный файл, fsync, rename; права
файла сохраняются, новый — 0600; прочие ключи, в т. ч. `rtsp_urls`, не трогаются; нечитаемый файл не перезаписывается).
Повторный выбор активного источника сохраняет его настройки (режим, формат, стандарт); новое устройство V4L2 —
`mode/format/standard: auto`. Журнал блока: `video select '<id>' (req N): ok|unknown-id|error[: причина]`.
Пример конфигурации:
`{"source": "synthetic", "rtsp_urls": ["rtsp://192.168.77.50:554/stream1", {"url": "rtsp://192.168.77.2:8554/cam",
"codec": "mjpeg", "name": "Тестовый RTSP"}]}`. Элемент `rtsp_urls` — строка (кодек h264) или объект
`{url, codec?, transport?, latency_ms?, timeout_s?, name?}`.

**Транспорт RTSP (S5, RTSP backend 1.0).** Ключ `transport` в описании (`{"source": "rtsp", …, "transport": …}`) и
в объектах `rtsp_urls`: `"auto"` (по умолчанию) | `"tcp"` | `"udp"`; другое значение — `ValueError` при открытии
(источник `Unavailable`, состояние `error` с причиной, как у неверного `codec`); учётные данные не попадают ни в
id/name/device/info, ни в сообщение об ошибке. Отображение на `rtspsrc protocols` (`videoinput.RTSP_PROTOCOLS`):

| transport | rtspsrc | поведение (проверено на rtspsrc 1.28.8, Mac; на платах 1.26.2 — логика та же, проверить на стенде) |
|---|---|---|
| `auto` | `protocols=udp+tcp`, `timeout=timeout_s` | SETUP по RTP/AVP (UDP); ответ **461 Unsupported Transport** → немедленный повтор SETUP по RTP/AVP/TCP в том же сеансе (~0,5 с до кадров); UDP принят, но датаграмм нет `timeout_s` (фаервол/NAT) → rtspsrc сам переподключается по TCP (кадры через `timeout_s` + ~1 с) |
| `tcp` | `protocols=tcp` | только RTP/AVP/TCP interleaved (прежнее поведение); сервер только с UDP → `No supported stream was found`, конвейер завершается → `error`, повтор с отступом |
| `udp` | `protocols=udp`, `timeout=timeout_s` | только RTP/UDP unicast; 461 → `error` (как выше); UDP без данных `timeout_s` → `Could not receive any UDP packets … No other protocols to try`, конвейер завершается → `error` (не зависание) |

`rtspt://` — только TCP (схема rtspsrc): `auto` там значит `tcp`, `udp` — ошибка описания. Потеря сервера при UDP:
соединение RTSP закрывается, rtspsrc завершается, `present()` (TCP) не проходит → `connect-error`, возврат →
`streaming` (как при TCP). Порты UDP клиента — случайные (rtspsrc `port-range` не задаётся): на блоке нет
фаервола, входящие датаграммы приходят на eth0 (схема — `S5-network-camera.md`).

**Фактический транспорт** — `status.video.source.transport` (`"tcp"`|`"udp"`|`""`) и `transport_mode` (заданный
`auto|tcp|udp`; у не-RTSP — `""`), `Ingest.status()`. `transport` непустой только в `streaming` и только когда
транспорт однозначен — `tcp`/`udp` (другого rtspsrc не пробует). **Ограничение:** при `auto` — `""`: конвейер идёт
через `gst-launch-1.0 -q`, предупреждение rtspsrc о переходе на TCP подавлено, а выбор после 461 не сообщается
вовсе; надёжно узнать без переделки нельзя. Точка расширения, если понадобится: процесс с GstBus (python3-gi на
блоке нет) или `GST_DEBUG=rtspsrc:4` в окружении конвейера и разбор stderr (`Ingest._read_err`), либо сопоставление
сокетов процесса конвейера (`/proc/<pid>/fd` ↔ `/proc/net/udp`) — только Linux. Санитайзер пульта
(`link/client.py::_sanitize_video_source`) новые поля пока отбрасывает — пульту они не нужны для работы.

Проверка: `tests/unit/test_rtsp_transport_unit.py` (конвейер по режимам, неверные значения, `rtspt`, `rtsp_urls` →

**RTP/UDP-источник без RTSP** (сырой поток на порт, без сеанса) — не реализован: `SOURCE_KINDS` =
synthetic|v4l2|uvc|rtsp. Нетривиально:
UDP без соединения — нет проверки присутствия (только «нет сигнала»), нужны caps из конфигурации (кодек, PT,
clock-rate, sprop), привязка порта и его конфликты, открытый UDP-приёмник по сети противоречит ADR-0011. Если
понадобится — отдельный kind `rtp` (`udpsrc address=… port=… caps=…` → депакетизатор), приём только с адреса из
конфигурации, состояние по потоку кадров.

**Стенд без захватов**: `tools/probe/s4_rtsp_test_server.py` — синтетический RTSP-источник (videotestsrc +
timeoverlay + clockoverlay + метка; нужны только python3 и gst-launch-1.0: есть на pi1 и pi2, gst-rtsp-server и
python3-gi не нужны). Элементы проверены по спискам пакетов образов `ci-57e8fe4-dev` и `devbox-b1d95a2`:
`gstreamer1.0-plugins-base` (videotestsrc, videoconvert), `-good` (jpegenc, rtpjpegpay, rtph264pay, rtpstreampay,
rtspsrc, v4l2h264enc), `gstreamer1.0-x` (pango: timeoverlay/clockoverlay/textoverlay), `-tools`; x264enc и avdec_h264
(ugly/libav) в образе нет — H.264 на плате только `v4l2h264enc`. Запуск (например, на pi1, источник для блока pi2):
`python3 tools/probe/s4_rtsp_test_server.py --port 8554 --codec mjpeg --label PI1-RTSP` (печатает адрес и строку для
`rtsp_urls`; S5: `--transports tcp,udp|tcp|udp` — какие транспорты принимать в SETUP, `--udp-drop` — «фаервол»,
`--codec h264` — первый доступный кодер, на Pi `v4l2h264enc`; `--check` — только проверить элементы; `--outage 30:10` — каждые 30 с сервер «падает» на 10 с: потеря и
возврат источника без ручной остановки; `--pidfile` — для остановки по ssh). С Mac:
`scp tools/probe/s4_rtsp_test_server.py pi1:/tmp/`; старт `ssh pi1 'nohup python3 /tmp/s4_rtsp_test_server.py --port
8554 --label PI1-RTSP --pidfile /tmp/s4-rtsp.pid >/tmp/s4-rtsp.log 2>&1 &'`; стоп `ssh pi1 'kill $(cat
/tmp/s4-rtsp.pid)'`. На блоке: добавить адрес в `rtsp_urls`, `systemctl kill --kill-whom=main -s
HUP sheregesh-remote-net` (или перезапуск), затем на пульте выбирать synthetic ↔ `rtsp:0`; остановка сервера → у
источника `connect-error`, запуск → `streaming`.
