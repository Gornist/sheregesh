# S5. Сетевая (Ethernet) камера на удалённом блоке

Статус: схема и расчёт; программная часть — RTSP backend 1.0 (`S3.3-universal-video-input.md` §13, «Транспорт
RTSP»). **Испытание с реальной камерой — BLOCKED: камеры нет.** Проверено только с тестовым сервером стенда
(`tools/probe/s4_rtsp_test_server.py`, RTP/TCP и RTP/UDP, MJPEG и H.264) на Mac и в CI.

## 1. Задача

К удалённому блоку (Raspberry Pi 4, один встроенный порт `eth0`, 1 Гбит/с) подключить IP-камеру с RTSP и при этом
сохранить связь пульт ↔ блок (канал управления TCP 7700 и защищённое видео TLS 7444, ADR-0007/0011) — по тому же
кабелю, без второго сетевого интерфейса.

## 2. Схема (предпочтительная)

```
  IP-камера (RTSP, H.264)             пульт (Pi 4, eth0)
        │ 10/100/1000                      │
        └──────────┐            ┌──────────┘
             ┌─────┴────────────┴─────┐
             │ неуправляемый коммутатор│  5 портов, 100/1000 Мбит/с, питание 5–12 В
             │ (PoE — если камера PoE) │  (одна широковещательная область, VLAN не нужны)
             └───────────┬─────────────┘
                         │
                  удалённый блок (Pi 4, eth0)
```

- Одна подсеть /24, без шлюза, DNS и DHCP-сервера не требуется: все адреса статические. Камера — RTSP-сервер,
  блок — клиент (`rtspsrc`); пульт с камерой напрямую не работает: видео камеры он получает только от блока по
  защищённому каналу (ADR-0011), как и любой другой источник.
- Коммутатор — обычный неуправляемый (гигабитный, чтобы порт блока не стал 100 Мбит/с); если камера питается по
  PoE — коммутатор с PoE (802.3af) или отдельный PoE-инжектор на порт камеры. Прямое соединение камера–блок
  кабелем возможно только вместо пульта, поэтому не рассматривается.

## 3. Адресация

| Узел | Изолированная лабораторная подсеть (ADR-0007) | Стенд 2026-10 (домашняя LAN) |
|---|---|---|
| пульт | 192.168.77.1/24 | 192.168.1.92 (pi1) |
| удалённый блок | 192.168.77.2/24 | 192.168.1.171 (pi2) |
| IP-камера | 192.168.77.50/24 (статический, задаётся в веб-интерфейсе камеры) | резервация DHCP на роутере по MAC камеры, например 192.168.1.50 |
| ноутбук инженера (необязательно) | 192.168.77.10/24 | по DHCP |

- Изолированная подсеть: всё статическое, адреса камеры и блока записываются в паспорт стенда. Камера с завода
  обычно имеет свой адрес (часто 192.168.1.64/.108/.10) или DHCP — сменить его до подключения (ноутбуком через тот
  же коммутатор) и выключить у камеры UPnP/P2P/облако.
- Домашняя LAN стенда: адреса пульта, блока и камеры — резервации DHCP на роутере (стабильные адреса без настройки
  устройств). Блоку адрес камеры нужен только в `video-input.json`.

Конфигурация блока (`~/.config/sheregesh/video-input.json` пользователя службы):

```json
{"source": "synthetic",
 "rtsp_urls": [{"url": "rtsp://user:password@192.168.77.50:554/Streaming/Channels/101", "codec": "h264",
                "transport": "auto", "name": "Камера мачты"}]}
```

Выбор на пульте — кнопка «Видео» → `rtsp:0` (или `python3 -m sheregesh.link.videoselect rtsp:0`). Пароль камеры
есть только в этом файле (права 0600); в телеметрию, журнал и имена источников он не попадает.

## 4. Трафик и порты на `eth0` блока

| Поток | Направление | Протокол/порт |
|---|---|---|
| RTSP-сеанс (OPTIONS/DESCRIBE/SETUP/PLAY, keepalive) | блок → камера | TCP 554 (или порт из URL) |
| RTP видео, `transport: udp` или `auto` | камера → блок | UDP: с server_port камеры на client_port блока (случайная чётная пара, выбирает rtspsrc) |
| RTCP | обе стороны | UDP client_port+1 / server_port+1 (несколько десятков байт/с) |
| RTP видео, `transport: tcp` | камера → блок | внутри TCP 554 (interleaved) |
| канал управления | пульт → блок | TCP 7700 (mTLS) |
| защищённое видео | пульт → блок (соединение), данные блок → пульт | TCP 7444 (TLS 1.3) |

На блоке нет фаервола, входящие UDP на случайные порты приходят. Если фаервол появится — либо разрешить UDP от
адреса камеры, либо задать `transport: "tcp"` (при `auto` rtspsrc сам перейдёт на TCP через `timeout_s`, 5 с по
умолчанию). Мультикаст не используется (`protocols` без `udp-mcast`), поэтому неуправляемый коммутатор без IGMP
snooping не «зальёт» сеть.

## 5. Влияние на канал пульт ↔ блок

Порты коммутатора полнодуплексные, у каждого направления своя полоса. Через порт блока проходят: **вход** — RTP
камеры + команды пульта; **выход** — видео к пульту (поток камеры без перекодирования, если кодек совпадает: H.264
→ H.264, MJPEG → JPEG) + телеметрия. Видео камеры и видео к пульту идут в разных направлениях и не конкурируют.

Оценка при камере ≤ 8 Мбит/с (H.264 1080p30 у типовых IP-камер 2–8 Мбит/с; собственный кодер блока —
6 Мбит/с, `video.py: video_bitrate=6000000`):

- порт блока 1 Гбит/с: вход ≤ 8 Мбит/с + управление (единицы кбит/с) ≈ 0,8 %; выход ≤ 8 Мбит/с ≈ 0,8 %;
- порт камеры 100 Мбит/с (часто у камер): 8 %; порт пульта: выход к пульту ≤ 8 Мбит/с;
- задержка в коммутаторе при такой загрузке — микросекунды; очереди не образуются.

**QoS не требуется** при ≤ 8 Мбит/с (и практически до десятков Мбит/с): узкого места нет ни на одном порту,
heartbeat 7700 и видео 7444 — разные соединения (ADR-0011), блокировки по очереди не возникает. Риск — только
MJPEG-камеры высокого разрешения (1080p MJPEG — 30–60 Мбит/с): канал выдержит, но лучше H.264 или
640×480/720p MJPEG. Общий широковещательный трафик в изолированной подсети пренебрежимо мал; в домашней LAN — тоже
(mDNS/ARP — кбит/с).

## 6. Почему не нужен второй интерфейс

- Полоса: см. §5 — один гигабитный `eth0` загружен < 1 %.
- Адресация: одна подсеть, маршрутизация не нужна; второй интерфейс потребовал бы второй подсети, правил
  маршрутизации и настройки NetworkManager/systemd-networkd в образе (RAUC A/B — новый образ).
- Надёжность: USB-Ethernet на Pi 4 делит шину USB с захватом V4L2 (UVC/HDMI→USB) и добавляет точку отказа
  (горячее отключение, переименование интерфейса); TL-003 уже исключил UE300 из эталона.
- Изоляция камеры, если нужна, достигается проще: камера без шлюза и облака в изолированной подсети; данные камеры
  блок принимает только по сеансу RTSP, который он сам открыл.

## 7. Запасной вариант: USB-Ethernet

Только если коммутатор поставить нельзя (например, нет места/питания): USB-адаптер (USB 3.0, RTL8153/AX88179) на
блоке, камера — напрямую кабелем в адаптер, отдельная подсеть (например, блок 192.168.78.1/24 на `eth1`, камера
192.168.78.50/24), пульт — по-прежнему на `eth0`. Нужно: статический адрес `eth1` в образе, имя интерфейса по MAC
(udev/systemd.link), проверка нагрузки USB вместе с захватом V4L2. Программная часть не меняется (в URL — адрес
камеры в своей подсети). Не испытывалось.

## 8. Проверка

  недоступен, «фаервол», потеря/возврат сервера.
- На стенде (главный агент): тестовый сервер на pi1 как «камера» (`--transports tcp,udp|tcp|udp`, `--udp-drop`),
  блок pi2 — `rtsp_urls` с `transport`; ожидаемое — `S3.3` §13, таблица транспорта.
- С реальной камерой — **BLOCKED** (нет камеры): подключение по §2–3, `transport: auto`, проверить `streaming`,
  `stream_width/height`, отсутствие обрывов heartbeat пульта в течение 30 мин, `tcpdump -ni eth0 udp` на блоке
  (RTP идёт по UDP), затем `transport: tcp`.
