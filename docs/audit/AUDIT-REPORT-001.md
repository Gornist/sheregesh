## 1. Executive Summary

«Шерегеш» 1.0 — лабораторный прототип из двух устройств на Raspberry Pi 4B: пульт с сенсорным экраном 10,1″ и удалённый вычислительный блок в герметичном FDM-корпусе. Они связаны проводным Ethernet и работают только с эмуляторами и синтетическими данными. ПО ориентировано на офлайн-работу, атомарную конфигурацию, A/B-обновления с подписью и доказательную приёмку.

**Готовность документации.** Требования **для старта программной части готовы примерно на 70 %**, для аппаратной части (CAD и закупки) — **нет** [В].
- Сильные стороны [Ф]: чёткая граница применимости; честные статусы (`NOT TESTED`, «не утверждено»); три реестра требований (SRS, JSON, CSV) **полностью совпадают** — 89 REQ, 78 Must, 10 Should, 1 Could; пересчёт бюджета совпадает с README (65 308,32 ₽).
- Слабые стороны: матрица испытаний — заглушка (TEST-ID = REQ-ID, нет методов и оборудования); у 33 из 78 Must критерий PASS нужно уточнить; не выбрано питание пульта; нет испытательной базы для IP54 и климатики; не решены модель доверия к подписи и роль удалённого блока без экрана.

**Кода для v1.0 нет.** Ветка `v2` пуста. Прежний код в архиве — RK3399/Armbian и радиоуправление (ELRS/CRSF, 6S LiPo). Он вне границы 1.0 и переносу не подлежит; можно переиспользовать только отдельные шаблоны.

**Главные риски:**
1. Питание пульта — связка из пяти Must, ни одна позиция не выбрана; на неё остаётся около 9 тыс. ₽ бюджета.
2. Удалённый блок: IP54 + пассивное охлаждение + PETG + +40 °C одновременно — физически напряжённое сочетание.
3. Ключ подписи в CI без ручного шлюза, при этом закреплённый в образе корень нельзя сменить без перепрошивки.
4. Must, для проверки которых нужно внешнее оборудование или люди (IP54, климатика, независимая сборка), а бюджета и исполнителей нет.

Начинать программную разработку можно уже сейчас, на x86 с эмуляторами: конфигурация, протокол, эмуляторы, GUI-каркас. Аппаратный трек сначала должен пройти три пробы: дисплей, питание, тепловой макет.

### 5.3. Достаточность для CAD, закупки и сборки

- **CAD пульта — недостаточно.** Нет габаритов и массы аккумулятора и системы питания, нет органов ввода. Нужны механический чертёж дисплея (размер 239×147 мм из старой ведомости требует сверки), положение кнопок OSD, схема вентиляции.
- **CAD удалённого блока — недостаточно.** Не определены граница IP и вводы (AUD-003) и тепловая схема (AUD-004).
- **Закупка — частично.** Стендовый комплект ПО (2×Pi, 2×microSD, 2×БП, дисплей, патч-корд) определён достаточно и не зависит от открытых вопросов. Рекомендую закупить его первым.
- **Безопасность сборки.** Принцип «только готовые защищённые изделия, без самодельной силовой части» сформулирован правильно и последовательно проведён в SRS, HARDWARE и BOM. Схему питания от 6S LiPo с самодельными понижающими преобразователями из прежнего проекта переносить нельзя.

### 5.4. Механика, питание, тепло — оценки [В]

- Мощность пульта ≈ 8–13 Вт. Для 4 ч нужно ≈ 40–60 Вт·ч номинала, для 6 ч ≈ 60–90 Вт·ч. Масса Li-ion изделия такой ёмкости — порядка 0,3–0,6 кг. Цель ≤2 кг достижима, но запаса немного.
- Удалённый блок: ≈ 4–6 Вт. Для 12 ч нужно ≈ 55–85 Вт·ч номинала.
- Пассивное охлаждение в PETG при +40 °C — главный физический риск. Тепловой макет нужно сделать до CAD.

### 6.3. Риск единого CI, подписывающего релизы

Единый CI удобен, но при одноуровневом ключе он становится единственной точкой компрометации всего парка устройств. Конкретные векторы [В]:
- скомпрометированный сторонний action или зависимость сборки;
- украденный токен сопровождающего с правом push тегов;
- PR из форка, получивший доступ к секретам при неверной настройке триггеров;
- self-hosted runner, исполняющий чужой код.

Поскольку корень закреплён в образе и не меняется по сети (UPD-003), восстановление после компрометации возможно только ручной перепрошивкой (UPD-008).

**Рекомендация:** офлайн-корень у владельца, промежуточный сертификат с коротким сроком в CI, подпись после ручного одобрения в защищённом Environment, подписывается проверенный артефакт с тем же хешом, actions закреплены по SHA, минимальные права, без секретов для PR, provenance/attestation и SBOM в релизе. Это закрывает GAP-010 и не отменяет REQ-UPD-007: CI по-прежнему единый, но с ручным шлюзом. Решение за владельцем (D1).

### 6.4. Предлагаемая архитектура (ADR-кандидаты, утверждает Tech Lead)

```text
Пульт                                              Удалённый блок
┌──────────────────────────────────┐               ┌───────────────────────────┐
│ sheregesh-gui (Qt6/QML, PySide6) │               │ sheregesh-agent           │
│   └ только IPC, без root         │               │  ├ диагностика, состояния │
│ sheregesh-core (asyncio)         │  TCP/JSON,    │  ├ видеоисточник (GStr.)  │
│  ├ config (YAML+schema, ревизии) │  hello/версия │  ├ приём обновления →     │
│  ├ diag / power-provider / fan   │◄────────────► │  │  RAUC (своя проверка   │
│  ├ link (пир, heartbeat, compat) │  heartbeat    │  │  подписи)              │
│  └ update (RAUC), backup (USB)   │               │  └ config (та же библ.)   │
│ systemd, journald, cage (киоск)  │               │ systemd, journald         │
│ RAUC + tryboot, root только чтен.│               │ RAUC + tryboot, root r/o  │
└──────────────────────────────────┘               └───────────────────────────┘
Эмуляторы (x86/CI): пир, питание, вентилятор/температура, неисправности, видео.
```

- Общая Python-библиотека (`config`, `protocol`, `diag`) — одна для обоих устройств и для эмуляторов.
- Пакеты Debian (`.deb`) из CI; образ собирается из закреплённого набора пакетов; использованные `.deb` архивируются.
- Сеть: статическая адресация изолированного стенда, Wi-Fi и BT выключены.

## 10. Decisions Required (только блокирующие)

**D1. Модель доверия для подписи релизов (AUD-005).** Блокирует первый образ с продуктивным ключом.
- **A (рекомендую):** офлайн-корень у владельца (аппаратный токен), промежуточный ключ в CI, подпись после ручного одобрения владельцем.
- **B:** ручная офлайн-подпись владельцем. Самый безопасный вариант, но меняет смысл REQ-UPD-007.
- **C:** как в SRS — один ключ в CI. Не рекомендую.

**D2. Испытательная база для IP54 и климатики (AUD-002).** Блокирует методику Must R-003/R-005.
- **A:** аккредитованная лаборатория. Расходы вне бюджета комплектующих.
- **B:** внутренняя методика по процедурам IEC 60529 с формулировкой «по внутренней методике».
- **Рекомендую:** B для итераций разработки; для финального протокола — A, если бюджет позволяет.

**D3. Роль удалённого блока без экрана (AUD-006, AUD-003).** Блокирует архитектуру и CAD удалённого блока. Подтвердить три пункта:
- (а) управление, обновление и экспорт журналов выполняются через пульт, Smoke Test удалённого блока — без GUI и ввода;
- (б) один индикатор за световодом, внешней кнопки нет;
- (в) внешняя АКБ — вне границы заявления IP54.

**D4. Профиль питания пульта (AUD-001).** Блокирует закупку и CAD пульта. Подтвердить:
- бесшовное переключение — обязательный признак изделия;
- замена батареи только на выключенном устройстве или при внешнем питании;
- готовность рассмотреть превышение лимита 50 000 ₽, если иначе Must не закрыть. Иначе придётся жертвовать Should 6 ч.

**D5. Публикация репозитория (AUD-009).** Блокирует публичный репозиторий. Рекомендую:
- перенести `archive/main-2026-10-22` в отдельный приватный репозиторий;
- открыть v1.0 с чистой историей;
- из архива ничего не переносить автоматически, код радиоуправления не переносить.
