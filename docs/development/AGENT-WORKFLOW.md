# Процесс разработки с агентами

## Контекст и источники

«Шерегеш» — открытая платформа для роботов, роверов и лабораторных платформ: пульт pi1 и удалённый блок pi2.
Решения владельца — `../decisions/DECISIONS.md`, требования — `../requirements/requirements.json`.
Архитектура — ADR и контракты; доказательства — датированные отчёты `../acceptance/`.
[PROJECT-STATE.md](PROJECT-STATE.md) указывает последний известный срез, а не текущее состояние живого стенда.
При конфликте не выбирай автоматически самый новый файл: проверь дату, commit, область решения и доказательство.
Решения D6/D7 и CHG-014/015 не заменяй прежними снятыми ограничениями.

## Начало и завершение задачи

1. Проверь `git status --short`, HEAD, ветку и незавершённую работу.
2. Зафиксируй цель, владельца файлов, критерии готовности и проверки по [шаблону передачи](SESSION-HANDOFF.md).
3. Независимые изменения выполняй в отдельном worktree. Составление контракта и интеграция общих файлов имеют одного владельца.
4. Перед коммитом просмотри `git diff` и `git diff --cached`; используй `git add <явные пути>`.
   Общие `git add -A`, `git commit -a` и `-am` могут включить чужие изменения.
5. Итог содержит изменение поведения, выполненные команды и результаты, пробелы и ссылку на доказательства.
   Завершение разработки, результат L4 и разрешение релиза — разные результаты.

## Проверки

Стандартная библиотека Python 3.11+:

```sh
python3 tools/reqs/reqgen.py validate
python3 tools/reqs/reqgen.py generate --check
python3 -m unittest discover -s tests/tools -p 'test_*.py'
python3 tools/security/scan.py secrets
```

ПО: окружение из `tools/ci/requirements-dev.txt`, Linux-зависимости Qt/GStreamer — в `.github/workflows/ci.yml`.

```sh
QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software .venv/bin/python -m pytest -q tests/unit tests/system tests/gui
```

Запускай сначала проверки затронутой области. Ошибка окружения и SKIP не являются PASS.
На macOS часть Linux/systemd/V4L2-сценариев неприменима: запиши ограничение и проверь в Linux/CI.
`reqgen.py gate` — отдельная релизная проверка; ожидаемый NO-GO не запрещает разработку.
Производные SRS/TEST-SPEC/матрицы меняются через реестр и reqgen. Подтверждение Must требует предусмотренного уровня и доказательств.

## Аппаратура и сборка

[STAND-WORKFLOW.md](STAND-WORKFLOW.md) описывает владельца стенда, ограниченные прогоны и восстановление.
Образы собираются на devbox, не на Mac; крупные передачи — напрямую между узлами LAN.
Изменение Python/QML обычно идёт через подписанный DEV deploy, изменение ro-установщика, пакетов и unit — через новый образ.
Проверяй весь жизненный цикл служб роли, включая video-tx/rx; цель current сама по себе не доказывает версию процесса.
Не выполняй устаревший workaround из памяти, если он уже заменён в установленном образе.

## Автономность

Выполняй согласованный объём без повторных запросов уже предоставленных полномочий.
При недоступности аппаратуры продолжай независимые локальные проверки.
Историческое разрешение на конкретный спринт — контекст того спринта, а не бессрочное правило для любых OTA.
В длинной работе сообщай результат этапа, текущую операцию, тайм-аут и следующий критерий завершения.
Skills описывают процедуру поверх инструментов, не дублируют код и реестр.
