# Пульт «Шерегеш» 10.1 (RK3399): что изучено и сделано в v1

Источник: ветка `archive/main-2026-10-22` (43 коммита, 19–22.10.2026) и локальные материалы владельца (`analysis/`, `reference/`, `legacy-vendor-services/`, `~/sheregesh-backup/`). Для платформы 1.0 всё это `obsolete` (см. `legacy-register.md`), но как знание об изделии и как готовые наработки годится для передачи.

Колонка «Можно отдать»: **да** — наша работа, отдаётся как есть; **да, без вендорских данных** — наша работа, но содержит выдержки из вендорских дампов, отдавать после вычистки; **нет** — вендорский код, бинарники, дампы или секреты, лицензия не подтверждена.

## 2. Что выяснили о железе (находки, которых нет в документации вендора)

1. **PMIC INT — GPIO4_C5**, а не GPIO1_C5 из pinctrl вендора (это копия референса). С GPIO1_C5 шторм `irq nobody cared` (~100 тыс. прерываний), ядро отключает прерывание PMIC.
2. **MAC Ethernet одинаковый на всех пультах** (`36:08:ad:27:42:78`, зашит в U-Boot/DT). Решение: MAC из SHA-256 eFuse CPU ID (локально администрируемый), служба до сети.
3. **TC358775 без I2C** (шины 0–4 просканированы), только через DSI. Вендорская настройка: dual-link, 8 бит, SPWG/VESA, `PCLKDIV=3` (mainline для dual-link ставит 6), 129,5 МГц, 1982×1244 → **52,5 Гц**, подогнано под скорость DSI 780 Мбит/с на линию. Полная расшифровка 27 регистров — `docs/HARDWARE.md`.
4. **Драйвер панели писать не нужно:** вендорский `panel-simple-dsi.ko` (автор iamdrq) — это `panel-simple-dsi.c`, который Armbian уже несёт патчем в 6.18. Init-последовательность берётся в DT.
5. **Мерцание панели было свойством вендорского ядра/драйвера DSI:** на 6.18 с теми же таймингами и ШИМ 1 кГц не мерцает.
6. **BQ25700A = BQ25703A с SMBus-адресами регистров.** Драйвер `bq257xx` подходит после трансляции адресов; патч ~125 строк. Лимиты вендора: заряд 2,944 А / 8,4 В, вход 3,3 А; драйвер ставит MinSystemVoltage 6,4 В из DT батареи. Fuel gauge нет — процент только оценкой по напряжению.
7. **Bluetooth BCM4345C5 не принимает >3 Мбод** (команда перехода на 48 МГц отвергается): `max-speed = 3000000`, LPO-клок от PMIC в порядке.
8. **HDMI работает**, хотя у вендора маршрут VOP→HDMI выключен (с опечаткой в `status`). Некоторые мониторы не принимают предпочитаемый 4K — фиксировать `video=HDMI-A-1:1920x1080@60`.
9. **PCIe x4 разведён, устройств нет**, обучение линка даёт ~5 с таймаута — выключен.
10. **`PwrOnState`** — gpio-hog GPIO4_D5 output-high при каждой загрузке (назначение не документировано, перенесено как есть).
11. **Питание модема MD515x / «Vektor» — GPIO2_A7** из userspace (в вендорских скриптах фигурирует как `GPIO7` на gpiochip2 и «GPIO71» — одна линия).
12. **U-Boot с eMMC берёт SD раньше eMMC** — новую систему можно гонять с карты, не трогая eMMC.
13. **Логотип U-Boot читается с `/boot` eMMC** (`splashfile=/boot/splash.bmp`, BMP 955×320 32 bpp, по центру) — меняется одним файлом на ext4, сам U-Boot не трогается.
14. MCU-джойстик определяется как физическая клавиатура — это ломает автопоказ экранных клавиатур.

Открытыми остались (нужна схема платы): назначение UART4; предупреждение `DAPM unknown pin Headphones`; кнопки L1/R2/cam_reset/bottom_cam_h/v не проверены.

## 3. Что выяснили о вендорском ПО

* **Архитектура:** MCU → `gdc-virtual-sbus` (evdev → калибровка → виртуальный HID `cafe:5005` для Pilot-S + SBUS по UDP 25 байт ~80 к/с на борт `192.168.1.15:9999`); `gdc-modem-ctrl-sib-ground` (gRPC :5691, MD515x через CH340, бортовая половина по gRPC); `mavlink-routerd` (UDP :14552 → бродкасты :14550, TCP :5760); GDCSettingsManager (PySide6/QML, gRPC); апдейтер GDC (A/B rootfs, MCU DFU, U-Boot).
* **Калибровка стиков** (`controls.json`) подходит без изменений к новой системе; алгоритм перенесён в Rust 1:1 и подтверждён 600 векторами, которые сгенерировал код вендора.
* **Ловушка модема:** в дампе конфигурации пароль пары замазан; служба с таким конфигом каждые 13 с перезагружает модуль, и тот циклически пропадает с USB. Пароль пары не заводской.
* **Ловушка сети модема:** вендорский профиль `192.168.1.14/27` перекрывает домашнюю сеть 192.168.1.0/24 и её шлюз — нужен `/32` + host-маршруты.
* «Залипающие» кнопки (`hold`) вендор сохраняет в `state.json` между запусками — небезопасно, в нашем демоне отказались.
* Экранная клавиатура вендора — расширение GNOME `gjsosk`, 70 % × 30 % экрана.
* Вендорские службы запускаются на Ubuntu 24.04 / Python 3.12 (колёса без зависимостей, `protobuf 5.27.2`, `grpcio 1.66.1`, `gpiod 2.2.1`, `pymavlink 2.4.42`); `mavlink-routerd` работает без пересборки.

## 5. Грабли сборки (переносимы на любой Armbian-проект)

* Docker-сборка Armbian требует binfmt qemu на хосте; регистрация слетает после перезагрузки хоста.
* Контейнер видит loop-устройства по снимку `/dev` на старте: если хост занял все loop за время сборки — «Unable to find free loop device».
* `/home` в образ кладётся только с `INCLUDE_HOME_DIR=yes`; Plymouth удаляется без `PLYMOUTH=yes`.
* Тема Plymouth `two-step` молча не попадает в initramfs без пакета `plymouth-theme-spinner` (нет `two-step.so`). Проверка: `lsinitramfs … | grep -c <тема>`.
* `update-initramfs` в `customize-image.sh` бесполезен (ядра ещё нет) — проверять на готовом образе через `debugfs`.
* Настройки Xfce нельзя править при живой сессии (`xfconfd` перезапишет); частичный `xfce4-panel.xml` у пользователя ломает панель по умолчанию; значки рабочего стола — канал `xfce4-desktop`, не `xfdesktop`.
* Автопоказ Onboard: AT-SPI + `keyboard-device-detection-enabled=false` (иначе MCU считается клавиатурой); Java/Compose-приложения клавиатуру через AT-SPI не вызывают.
* Не отвязывать `pwm-backlight` на лету: падает DRM до перезагрузки.
* Время: первая сборка ядра + rootfs ~80 мин, повторная с ccache ~17 мин.

## 6. Что не проверено в v1

Радио на реальном ESP32 / модуле ELRS (полудуплекс CRSF с диодом, телеметрия), `srb-head` на Pi и джиттер UART, видео на железе, failsafe борта, подпись кадров SRB1 (не сделана — только прямой кабель), установка на eMMC (полный образ eMMC так и не снят), смена временных паролей.
