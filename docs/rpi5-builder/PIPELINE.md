# Конвейер: этапы, проверки, загрузочный тест

## Модель задания

Задание = коммит (git bundle). Команда `submit` пакует коммит, копирует его на хост и ставит в очередь; единственный
исполнитель (`flock`) берёт задания по очереди. Состояние хранится в `jobs/<id>/state.json` (этапы, время, причина провала,
действовавшие выключатели), журналы — в `jobs/<id>/logs/`. Конечные состояния:

| Состояние | Значит |
|---|---|
| `PASSED` | все этапы прошли; созданы `shbuild-report.json` и артефакты |
| `FAILED` | дефект кода или образа (тест, сборка, гейт, загрузочный тест) |
| `ERROR` | сбой среды (диск, память, Docker, отсутствует эталон) |
| `CANCELLED` | отменено (`cancel`) |
| `TIMEOUT` | этап превысил предел времени |

`wait <id>` печатает ровно одну строку итога, код возврата 0 только при `PASSED` — по ней удобно ждать из скриптов
и агентов. Следите за **всеми** конечными состояниями, а не только за успехом.

## Этапы

| Этап | Что делает | Предел |
|---|---|---|
| `preflight` | диск ≥ 40 ГБ; ОЗУ + свободная подкачка на диске ≥ 6 ГБ при ОЗУ ≥ 1 ГБ (zram не считается); Docker жив; нет чужой сборки | 1 мин |
| `checkout` | `git worktree` коммита из пакета; `SOURCE_DATE_EPOCH` — время коммита | 5 мин |
| `tests` | `python3 -m unittest discover -s tests/tools` | 15 мин |
| `build` | `os/docker-build.sh` (контейнер arm64, rpi-image-gen), внутри `os/build.sh`: образ, проверка структуры, сжатие `zstd`, SBOM, `SHA256SUMS`, `build-report.json` | 90 мин |
| `gates` | см. ниже | 30 мин |
| `boot` | загрузочный тест в QEMU | 30 мин |

Если образ собирается как образ самого хоста (`--config <имя>-buildhost-pi5`), проверки структуры и загрузки свои
(`verify_buildhost.py`, сценарий `buildhost`), а гейты владельцев/упорядочения и пакет приложения не применяются.

### Гейты

1. `build-report.json`: `verify_exit == 0`, `dirty == false`, тот же коммит, что в задании; итоги проверки структуры
   образа без `SKIP` и `FAIL` (пропущенная проверка — не PASS: нет `debugfs`/`mtools` в сборщике — образ не пройдёт);
2. `sha256sum -c SHA256SUMS`;
3. SBOM образа (SPDX 2.3) обязателен, проверяется;
4. `owners_check`: владельцы файлов корневой ФС против эталона (ловит сборку от root без пользовательских пространств
   имён — UID сборщика на системных файлах);
5. `order_check`: `systemd-analyze verify` юнитов ×8, циклов упорядочения нет. Перед прогонами проверка доказывает, что
   видит циклы: в оверлей кладётся заведомый цикл («канарейка»); не найден — проверка слепа, код 3, а не PASS.

Пункты 4–5 включаются проектом (скрипты `owners_check.sh`, `order_check.sh`, эталон в репозитории или в `~/shbuild/baseline/owners.txt`).

### Параллельность

Независимые этапы идут вместе: `tests ‖ build` (включено) и внутри `gates` `owners_check ‖ order_check` (включено).
Провал любого прерывает соседний (файл `abort` в каталоге задания); итог берётся от первого по порядку этапа.
`gates ‖ boot` — опционально, по умолчанию **выключено**: на 2 ГБ ОЗУ старт KVM рядом с гейтами падает
`KVM_CREATE_VM: Cannot allocate memory`.

## Загрузочный тест

QEMU `virt` (aarch64) с **ядром Debian** и его модулями (набор делает `make_vmkit.sh` один раз при установке), диск —
весь образ, поверх него qcow2-оверлей (образ не меняется). Внутри — настоящий systemd образа: пространства имён,
cgroup и песочница юнитов как на реальной плате (в контейнере с эмуляцией пользовательского режима они падают ложно).

- Контейнер без `--privileged`; сеть — tap + мост + dnsmasq внутри контейнера; дамп трафика `tcpdump`.
- Гостю выдаётся минимальный `initramfs` (busybox, модули виртуальных устройств): монтирует корень образа, кладёт
  в `/run` юнит-пробу и делает `switch_root` в `/sbin/init` образа. В самом образе ничего не меняется.
- Проба `vm/probe.sh` печатает строки `SHBOOT ключ=значение` в отдельный канал virtio-serial; `boot_check.sh` проверяет
  их: состояние системы, упавшие юниты (допустимые — явным списком с причиной), имя хоста, сеть/DHCP, sshd, нужные
  службы. Потерянная строка пробы — провал, а не «пусто = хорошо».
- Сценарий = одна машина с одним набором условий; проект задаёт свои, для образа хоста есть готовый `buildhost`
  (корень — раздел 2 MBR, расширение корня, Docker отвечает, инструменты, подкачка).
- **KVM:** гость идёт на реальном процессоре (`-cpu host -accel kvm`), нужен `/dev/kvm`. `SHBOOT_NO_KVM=1`
  принудительно включает программную эмуляцию (TCG) для сравнения и отладки. Образ распаковывается один раз на задание (разреженный файл), паузы
  пробы — ожидание по условию (адрес получен + 5 с), а не фиксированные.

Не проверяется: прошивка, ядро Raspberry Pi, GPU/дисплей, GPIO/UART, A/B-откат загрузчика — это остаётся за платами.

## Артефакты и хранение

`~/shbuild/artifacts/<коммит>[.<конфигурация>]/`: `*.img.zst`, `*.sbom.zst`, `SHA256SUMS`, `build-report.json`,
`verify.json`, `owners.txt`, и только при `PASSED` — **`shbuild-report.json`**. Хранятся последние 5 `PASSED` и всё с файлом
`keep`; артефакты провалов удаляются. `fetch <id>` копирует артефакты `PASSED` на компьютер (`rsync` по SSH).

Допуск на железо — по `shbuild-report.json`: состояние `PASSED`, все обязательные этапы `PASS`, коммит совпадает с
коммитом образа. Инструменты записи и раскатки вашего проекта могут требовать его (`tools/build/gate.py`).
