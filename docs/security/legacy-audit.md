# Проверка прежней разработки перед отделением (решение D5)

**Дата:** 2026-10-22 · **Исполнитель:** Tech Lead · **Связано:** REQ-REL-011, DOC-007, AUD-009
**Объект:** все ветки репозитория `Gornist/sheregesh`: `main` = `archive/main-2026-10-22` (9612e9f, 43 коммита) и `v2`. Всего 45 коммитов и 281 уникальный blob во всей истории.
**Видимость репозитория на дату проверки:** private (GitHub API).

Это первичная проверка. Полную проверку по REQ-REL-011 выполняет автоматический сканер в релизном workflow перед открытием репозитория.

## 1. Метод

- Перебраны все blob всех коммитов всех веток (`git rev-list --objects --all`), а не только текущее дерево.
- Поиск по шаблонам: закрытые ключи (`BEGIN … PRIVATE KEY`), открытые SSH-ключи, токены GitHub/AWS/Slack, пароли, PSK Wi-Fi, `secret=`, `token=`, `api_key`.
- Проверены удалённые файлы (`--diff-filter=D`) и авторы коммитов.

## 3. Вопросы владельцу (не блокируют работу над 1.0, нужны до открытия репозитория)

1. Где хранится закрытый ключ `mac-claude`? Если он когда-либо покидал ваш Mac (devbox, облачные сессии, общий диск), его нужно отозвать: удалить открытую часть из `authorized_keys` всех устройств и сервисов (включая GitHub, если ключ туда добавлен) и создать новый ключ. Если он не покидал Mac, отзыв из-за этого репозитория не требуется. Но ключ всё равно стоит удалить с устройств прежней платформы, если они больше не обслуживаются.
2. Есть ли работающие устройства с образом прежней платформы (пароль `sheregesh`)? Если есть — смените пароли (F2).
3. Допустимо ли, что публичная история `v2` содержит ваш адрес электронной почты (F6)? Иначе до публикации история переписывается с адресом `noreply`.

## 4. Порядок отделения архива (выполняется перед открытием репозитория)

Действия необратимы и затрагивают удалённый репозиторий. Выполняются только по отдельной команде владельца.

1. Создать отдельный приватный репозиторий архива и выполнить `git push --mirror` всех веток и тегов.
2. Проверить копию: число коммитов и хеши веток совпадают, клон проходит `git fsck`.
3. В основном репозитории сделать ветку `v2` веткой по умолчанию; удалить `main` и `archive/main-2026-10-22`.
4. Убедиться, что в основном репозитории не осталось объектов архива: свежий клон и `git rev-list --all` содержат только историю `v2`. Учесть, что GitHub может хранить старые объекты в форках и кэшах PR — для полной гарантии открывать **новый** репозиторий с историей `v2`, а не менять видимость текущего.
5. Выполнить проверку REQ-REL-011 на новом репозитории.

Рекомендация Tech Lead: шаг 4 выполнить через новый публичный репозиторий. Тогда объекты архива гарантированно не попадут в публичную область.
