# ШЕРЕГЕШ — системные требования к версии 1.0

**Документ:** `SHEREGESH-SRS-1.0`
**Редакция:** Rev. B / 2026-10-22 (заменяет Rev. A от 2026-10-22, хранится в `docs/baseline/rev-a/`)
**Статус:** техническое задание для реализации; не свидетельство приёмки
**Программная платформа:** Raspberry Pi OS, Raspberry Pi 4B 4 ГБ (оба устройства)
**Источник требований:** `docs/requirements/requirements.json` — единственный источник. Раздел 4 генерируется из него. Изменения относительно Rev A перечислены в `docs/requirements/CHANGELOG-REQ.md`, решения — в `docs/decisions/DECISIONS.md`.
**Принцип:** всё, что ещё не испытано, имеет статус `NOT TESTED`. `NOT TESTED` не равен PASS.

> **Граница применимости.** Документ описывает пульт и удалённый блок для наземных платформ — роверов, роботов, лабораторных стендов — и лабораторный прототип с программными эмуляторами внешнего оборудования. Управление наземными платформами, в том числе по радиоканалу ELRS/CRSF, входит в назначение пульта (решение D6); архитектура канала управления и поведение при потере связи задаются отдельным ADR.

## 1. Цель и комплект поставки

«Шерегеш» — открытая воспроизводимая DIY-платформа из **пульта** и **удалённого вычислительного блока**. Версия 1.0 предоставляет:
- двуязычный локальный интерфейс на пульте;
- физический и сенсорный ввод;
- проводной обмен безопасными тестовыми данными;
- отображение синтетического видеопотока;
- диагностику;
- конфигурацию в YAML;
- автономное резервное копирование;
- A/B-обновления с подписью;
- отчётную лабораторную приёмку.

Эталонная сборка обходится без заказных печатных плат: она опирается на документированные готовые модули и FDM-детали. Бюджеты раздельные: ориентир **50 000 ₽ на пульт** и **50 000 ₽ на удалённый блок** (Should). Самостоятельно увеличивать бюджет нельзя. Если выполнение Must требует превышения, владельцу представляется сравнительная смета (решение D4).

**В v1.0 не входят:**
- веб-интерфейс администрирования (v1.1/v1.2);
- неподтверждённые эксплуатационные функции;
- автоматические исправления файловой системы с потерей данных;

## 2. Приоритеты и доказательства

- **Must** — обязательное свойство. Перед `Stable` нужен подтверждённый `PASS` по всем связанным TEST-ID на требуемом уровне доказательства.
- **Should** — целевой параметр. Отклонение измеряется и обосновывается; Stable автоматически не блокирует.
- **Could** — дополнительная возможность; допускается невыполнение.
- **Won't** — функция явно исключена из v1.0.
- **TBD** — решение не принято. Если оно затрагивает Must, его закрывают до начала соответствующей реализации.

**Методы проверки:**
- **A** — автотест в CI с эмуляторами;
- **H** — стенд на эталонном оборудовании;
- **M** — ручное лабораторное испытание;
- **I** — инспекция или анализ;
- **X** — внешняя лаборатория.

**Уровни доказательства:**
- **L0** — только описано;
- **L1** — собирается;
- **L2** — модульные тесты;
- **L3** — эмуляция без эталонного оборудования;
- **L4** — эталонное оборудование или релизные материалы;
- **L5** — независимое подтверждение.

Для продуктовых Must, если не указано иное, требуется **L4**. Результат на уровне L3 (CI с эмуляторами) необходим, но для Stable недостаточен.

## 3. Логическая архитектура

```text
[Пульт: Raspberry Pi 4B / Raspberry Pi OS]
 ├─ GUI RU/EN, экран 1920×1200, сенсорный и физический ввод
 ├─ Конфигурация / диагностика / журналы / офлайн-справка — для обоих устройств
 ├─ Приём и отображение синтетического видеопотока
 ├─ Управление удалённым блоком: настройки, обновления, диагностика, экспорт журналов
 └─ Ethernet ─── изолированный лабораторный канал ─── Ethernet
                               │
[Удалённый блок: Raspberry Pi 4B / Raspberry Pi OS, без GUI и органов ввода]
 ├─ Агент диагностики, источник синтетического видео, эмуляторы
 ├─ Проверка совместимости версий; собственная проверка подписи обновлений
 ├─ RGB-индикатор состояния за световодом корпуса
 └─ Восстановление: сервисный доступ (REQ-R-009) и USB
```

Производительность, переносимость драйверов, временные характеристики и работа подключённого оборудования на Raspberry Pi 4B подтверждаются испытаниями. Архитектурные решения — `docs/adr/`.

## 5. Политика испытаний и релизов

1. До статуса Stable все `Must` имеют подтверждённые `PASS` с устойчивыми ссылками на доказательства. Гейт `tools/reqs/reqgen.py gate` должен выдать GO.
2. Для каждого релиза CI выполняется заново. Также проводятся Smoke Test **пульта** (TEST-SMOKE-P), **удалённого блока по его фактической конструкции** (TEST-SMOKE-R) и **их совместной работы на эмуляторах** (TEST-SMOKE-S).
3. Для неизменённых подсистем допускается перенос ручных результатов при наличии письменной оценки влияния изменений; исходный результат не стирается.
4. Протокол испытания содержит:
   - TEST-ID и REQ-ID;
   - идентификатор ПО и образа;
   - HW-версию;
   - дату и исполнителя;
   - метод, оборудование и условия;
   - результат и уровень доказательства;
   - ссылки на сырые журналы;
   - отклонения.
5. Отчёт о приёмке, журнал CI, ручные протоколы и обоснования переносов публикуются в **GitHub Releases** как файлы релиза. Опубликованные ранее отчёты не заменяются.
6. Требования меняются только через запись CHG в реестре со ссылкой на решение. Тихая смена приоритета для обхода блокирующего Must невозможна: генератор отклоняет изменения без записи.
7. Испытания IP и климатики по внутренним методикам называются «по внутренней методике» и не выдаются за аккредитованную сертификацию.
